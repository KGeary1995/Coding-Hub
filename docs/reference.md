# Trace reference

How each part of Trace works, what it stores, and the release history. To install Trace and get started, see the [README](../README.md).

Trace (formerly AI Coding Hub) is a local Electron desktop workspace for running **Claude Code and OpenAI Codex CLI side by side**. This source release includes the multi-channel terminal grid, engine-specific settings, local persistence, file explorer, Git diff review, MCP management, skills/plugins inspection, usage history, shared handoff memory through Google Drive for desktop, a searchable AI help guide, and shared project rules for both engines.

## Codex model catalog and application stability (v1.7.2)

Codex channel settings now load the full model catalog reported by the installed official CLI, including additional/hidden models and every returned page. Suggestions use exact CLI model values, and reasoning controls show the selected model's advertised levels. Custom model IDs remain editable; blank fields retain CLI defaults. **Use Codex CLI defaults** clears resume metadata as well as model/reasoning overrides so recovery starts a fresh conversation while preserving the old conversation in native history.

Terminal rendering now defaults to software; optional WebGL acceleration is in Settings and applies after an app restart. Native event delivery is guarded during renderer loss, and display crashes offer reload after terminal cleanup. **Settings → Running application → Application stability & crash diagnostics** shows bounded local lifecycle records. Native crash dumps remain local and are excluded from memory sync, backups and support exports. The reported Windows application close during Claude use has not been reproduced or attributed to a specific cause; see [the release notes and validation limits](models-stability-v1.7.2.md).

## Code review and reliability fixes (v1.7.1)

This release fixes Git push destination review, short/overlapping Codex usage correlation, Unix child-process cleanup, linked design-task editing, large verification results, escaped memory/design records, memory limits and redirected storage, malformed MCP messages, repeated Drive scans, and signed upgrade baseline selection. Vitest is upgraded to remove the critical development-tool advisories found during review. See [the audit report](audit-v1.7.1.md) for reproduction evidence, validation, and outstanding Windows/provider checks and development-dependency advisories.

## AI coaching (v1.5.0)

**AI coaching** shows local usage trends, token totals, configured-price estimates, and heuristic suggestions. Add curated prompt examples and record successful/partial/failed outcomes; no full session logs are mined automatically. Select up to five examples and review the complete coaching report. Nothing is sent to a model by opening this screen or preparing a report.

**Live coaching** (on by default; **Coach my prompts as I send them** on the AI coaching screen) checks each prompt you send in a Claude Code or Codex channel, terminal or chat, as soon as the CLI writes it to its transcript. The checks run on this computer: a thin first prompt, a problem with no error text, a task with no way to tell it worked, "better" with no meaning, several asks at once, or a very long prompt. Slash commands and short replies get none. Up to two tips appear in a strip under that channel, and every prompt is listed, newest first, under **Live coaching** on the AI coaching screen, where **Save as example** adds it to your examples. **Ask AI** (on the strip or the list) sends that one prompt, and the end of the agent's reply before it, to Claude Haiku through Claude Code (`claude -p --model haiku`, no tools, no MCP servers) on that channel's Claude account (the default account for Codex channels), and to Codex (`codex exec` in a read-only sandbox, low reasoning) only when Claude Code is not installed: a Claude review takes a few hundred tokens, a Codex one about 24,000. Its usage counts in the status bar's **Today** and on the Usage screen: the review's session is kept, in `~/.coding-hub/coaching`, which Session history does not list. Another computer's channels are coached on that computer; their tips show on its tab here and on the phone, and **Ask AI** there has that computer's CLI review the prompt. It takes a few seconds and uses a little of your plan; it returns advice and a rewrite with `[placeholders]` for details only you know. Coached prompts are kept on this computer only (`coaching/live-tips.json`), for 30 days and at most 500; the screen lists the newest 50, sums up the last 7 days (how many prompts had each kind of tip, and the change that would help most), and **Clear coached prompts** forgets them. The switch is `coaching/live.json`. Trace's own coaching channels are not coached.

For deeper agent advice, explicitly approve the reviewed report and choose **Prepare Claude coaching** or **Prepare Codex coaching**. This creates an idle channel in a separate local report folder, with your shared rules applied. Choose its account/model, start it, finish any CLI trust/setup prompts, then click **Send coaching request**. The agent is asked to analyze the selected examples, suggest meaning-preserving rewrites, and propose measurable experiments. Advice appears in the interactive terminal and ordinary local session history. Provider CLI configuration/tools/approvals still apply; the prompt asks for analysis without commands, edits, or unrelated file access. This optional step uses provider inference and is not offline AI. Local heuristic findings are not labeled as AI advice, and token use alone does not establish outcome quality. Prompt examples and prepared reports remain under `~/.coding-hub/coaching`, outside curated Drive memory. The 100 most recent prepared coaching reports are kept; when another is prepared, the oldest folder not used by an open channel is deleted. Prompt examples are capped at 100. Prepared requests now persist with the workspace. After restarting, start the idle channel, handle CLI prompts, and explicitly send the retained request.

The setup guide dismisses automatically after a shared or independent project folder is configured, and can be dismissed manually. Completion is remembered in the desktop profile.

## Codex launch troubleshooting

Accounts & connections reports local login status, not verified model access or a successful interactive launch. On Windows, Trace prefers the native Codex binary inside official npm packages so ConPTY attaches directly to the console program; older JavaScript launchers remain a fallback and run with the installed Node.js (`node.exe` on PATH), because Electron's own executable shows no output in a Windows pseudoconsole. Native package executable entries are launched directly rather than interpreted as JavaScript. Failed coding runs preserve a bounded terminal diagnostic even when the CLI clears its alternate screen. A failed Codex tile offers **Use Codex CLI defaults**, clearing model and reasoning overrides before you retry.

If Codex still exits with code 1, read the error printed above the exit marker and shown in the channel's tile. In PowerShell, change to the same project folder and test `codex.cmd --version`, `codex.cmd login status`, and `codex.cmd` (use `codex` for native installations). Resolve the CLI's actual error, such as invalid local configuration, unavailable model, missing dependency, terminal compatibility, or provider access. Cloud fixture tests do not prove that a specific Windows/provider installation is fixed.

## Multiple Claude accounts (v1.4.0)

Open **Accounts & connections → Claude account profiles**. Add a name such as Personal or Work, then use **Connect Claude profile** and complete the official CLI login. Choose the intended account in the browser; browser cookies can preselect your current account. Repeat for your other accounts. Up to ten named profiles are supported, plus **Default**, which preserves your existing local CLI login.

In each Claude channel, open **Settings → Claude account profile**, select a profile, and start the channel. Connect a named profile before launching; the host verifies its CLI login and blocks unverified or signed-out profiles. Different profiles can run at the same time, within the existing channel limit. Stop a channel before changing its account. Reconnecting a named profile requires stopping channels using it; other profiles can continue. Labels can be renamed without changing login storage or saved channel assignments.

Named profiles use separate `CLAUDE_CONFIG_DIR` directories under `~/.coding-hub/claude-profiles/<profile-id>/`. The registry stores only profile IDs, labels, and creation dates. Claude Code handles credential storage and refresh; Trace does not copy, read, or export credential files. Authentication environment overrides inherited from the host are cleared for named profiles. The default login and other host environment variables are preserved. Project settings can still explicitly configure authentication helpers or environment values; review those if the CLI reports an unexpected account. Named profiles start with independent user settings, skills, and user MCP configuration; project-level instructions and integrations remain shared. Profile credentials are not included in curated Drive memory or source archives. Usage follows each profile's structured session logs, and profile choices are retained in local workspace/history settings.

Every Claude channel shows whose account it runs on, in that account's colour: a chip with the account's name in the tile's header and a stripe down the tile's left edge. A named profile shows its name. A channel on **Default** shows the name of the profile signed in to the same account (so it reads Personal when your default login is your personal account), or the account's email when no profile matches. To find out which account a login is, Trace reads only the email and organization from `.claude.json` (`oauthAccount`), never the credentials file. Phones and linked computers show the same name and colour for each channel.

Profile tests use isolated fixture CLIs to exercise separate logins, simultaneous PTYs, telemetry, reconnect protection, and restart persistence. Real subscription login and model completion must be verified on your desktop with your own accounts. Credential-directory behavior was inspected in Anthropic's published Claude Code 2.1.29 CLI; use a current official CLI.

## Run on Windows

Install **Node.js 24 LTS** (minimum 22.13), Git for Windows, and the official Claude Code and Codex CLIs. Authenticate each CLI using its normal login flow. Extract the source ZIP into a local development folder, then open PowerShell **in the folder containing `package.json`**:

```powershell
npm.cmd ci
npm.cmd run dev
```

`npm.cmd` avoids the blocked PowerShell `npm.ps1` wrapper without changing execution policy. Verify `claude --version`, `codex --version`, and `git --version` in the terminal used to launch the app. Use `claude.cmd` / `codex.cmd` for npm launchers if their PowerShell wrappers are blocked. Claude Code may require Git Bash according to its current Windows installation instructions.

After installation, `npm.cmd start` builds and opens the production app. Restart the app after installing a CLI, changing PATH, or editing native host source. Renderer edits reload during development.

## Account and project setup (v1.2.1)

Open **Accounts & connections** to connect Claude Code, OpenAI Codex, and GitHub before starting a channel. Refresh detects existing CLI sign-ins; Connect runs the official login command in a temporary interactive terminal. The CLI may open your browser or display a URL/code. Credentials remain with the provider CLI; login output is excluded from coding history and Drive memory. Account setup does not require a project or shared-rule application. Missing CLIs show installation guides and Windows commands; installing the app does not install the agent CLIs.

Open **Projects** to browse an existing folder, enter its absolute path, create a new local project, or list/clone GitHub repositories. A folder picker hides files; use **Use this folder** to select its current location. GitHub listing requires the local GitHub CLI (`gh`) and its own login; it lists up to 100 repositories for the account/selected owner. Cloning requires Git and a parent folder, preserves existing folders, and opens the new local copy. A channel's settings also offer **Independent repository** under **Working folder**, then **Choose folder**. Apply shared rules to the selected folder when rules are configured.

**Stop** now terminates a Windows channel’s process tree before closing ConPTY, verifies its launcher exited, and gives cleanup more time. Unix stops its process group with TERM/KILL escalation. A missing PTY exit event is recovered only after the process is verified gone. Account-login cancellation shares these safeguards. The terminal exits its alternate screen and disables input after exit; Stop failures keep the PID available and surface an error.

Windows packaging uses a fresh staging folder for every attempt, avoiding the locked `release/win-unpacked` rename failure. Verified installers/update metadata are then copied to `release/`; prior staging directories remain intact. `npm run verify:win` follows the last successful build manifest. A Windows workflow additionally installs two package versions, checks retained data, and uninstalls in an isolated runner.

A notice never covers a chat's message box and Send, or the tile you are typing in: then notices appear at the top right instead, under the tiles' headers and a conversation's bars. Where neither place has room (a long message in a short chat), they step aside until there is room; the status bar still shows who needs you.
- **Changes:** the changed files on the left, the diff in the middle and **Ship** on the right: commit, push and pull request. The file list stages (from 1.31.3; before, a second list in Delivery did): **+** stages a file, **−** unstages it, each group has **Stage all** or **Unstage all**, and **Filter files** narrows the list. The diff shows **Unified** or **Split** (side by side), and **Wrap** wraps long lines. **Review comments** (from 1.32.2): in Unified, the button at the start of a line (shown on hover or focus) opens a comment on it; **Add comment** (or Ctrl/Cmd+Enter) keeps it under the line. The bar above the diff counts them and sends them all as one message to a running agent channel working in that repository (its folder or one inside it; **Send to** picks which), typed in as you would type it: each comment with its file, line and code, then *Make these changes, or say why not.* Sent comments are cleared; they are kept while Changes stays open, not saved. A terminal waiting on an approval is not sent to, since the message's Enter would answer it. Ship ticks a step once done: Commit after a commit leaves nothing staged, Push while the branch has nothing left to push (its upstream, or the same branch on a remote, as Git last saw it), Pull request once one is created; the commit message and pull request fields clear once used. Each step still asks for native confirmation; there is no force push or discard. When the folder is not a Git repository the Delivery card is not shown; **Refresh changes** checks again. **Refresh changes** also reads the Delivery card again, and clears an error it showed (from 1.30.3; before, in a repository it kept the files it had read, and a step then failed as out of date). **History** (beside **Uncommitted** at the top) shows the commits of HEAD, the local branches and their upstreams, newest first and at most the latest 200, with a lane graph, badges for HEAD, branches, remote branches and tags, the short commit id, author and time. Choosing a commit (click, or Up/Down, Home/End) shows its full message and the files it changed against its first parent (up to 500), with lines added and removed. It only reads: nothing there checks out, merges or rewrites. It reads again with **Refresh changes** and after a commit from Ship; the diff and its review comments stay as they were while History is shown.
- **Usage:** pick a window (Today, 7, 14 or 30 days) and an engine. The strip totals input, output (with reasoning shown as part of it), cache reads, sessions and estimated cost, with the change from the previous window. The chart stacks each day's tokens by engine (cache excluded); the table lists each session with its context at the last report.
- **Agent setup:** Accounts, Shared memory, Shared rules, MCP servers, Skills & plugins and Settings share one screen. Every area in the list is one row of the same height. A dot on the Accounts icon shows whether its connections are signed in (green) or one still needs signing in (amber), and on Shared memory's whether it is on for every project; the words ("2 of 3 connected", "On for every project") are the row's tooltip and are read out with its name. Accounts lists Claude Code, Codex and GitHub as rows; **Back to channels** at the top returns to the workspace, as on Changes, Files and Session history.
- **Settings:** six sections, each reached from **On this page** under the heading: This app (running application, updates, local storage), Preferences (display, terminal, Drive memory folder, alerts and budget, model pricing), Engines and worktrees, Backup, Sync, and Phone and other computers. **Save preferences** is the Preferences section's footer: it stays at the bottom of the window while any field it saves (terminal, Drive folder, alerts and budget, model pricing) is on screen, and says which those are; Display and keyboard applies at once. Under **Other computers**, what another computer or a phone can see or do stays in view, and what each computer needs (reaching this one the way a phone does; for a shared screen, being on, awake and unlocked) is under **How this works**.

## Channel tiles

Each tile is a channel (CH1–CH4, in grid order). A tile is a card: its header, notices and footer are on the card, and the terminal (or the conversation) is a dark panel set into it. From top to bottom, a tile shows:
- **Header:** the engine's mark and the channel number in the engine's colour, the name (the channel's folder, unless you renamed it in its settings), what it is working on (the title its CLI gives its terminal, such as Claude Code's task summary), the model, and the Claude account it runs on (also a coloured stripe down the tile's left edge). Then the action for the current state, a **⋯** button that opens and closes the controls row, and the state badge. On a narrow tile the topic shortens first, then the model, then the account; the name goes last.
- **Controls row:** press **⋯** in the header to open a row under it with what the channel is doing ("Running", "Ended with exit code 1"), its folder, cost and context, and the Interrupt, Stop (or Restart), Conversation, Settings, Task, Duplicate, Maximize and Close buttons; press **⋯** again to close it. Hover over the facts for the process ID and the folder's whole path. The row has its own place between the header and the terminal and never covers the terminal's output (before 1.30 it appeared over the terminal's first lines while you pointed at the header). It stays open while the channel's settings or its **Conversation** is open, and while **Close** asks its question. On tiles 680 px wide or narrower the buttons show only their icons.
- **The terminal.** Before a channel starts, this area is not a terminal yet: on the card's own colour it shows the engine, one line about it, the channel's folder (which opens the channel's settings, or Projects when no project is open) and **Start**.
- **Footer:** at the left the channel's context (a meter and a percentage for Codex; for Claude Code only the tokens in context after the last reply, with no meter or percentage because Claude Code does not record its window size) and the channel's new tokens today (across restarts of the channel and of Trace: input outside the prompt cache, plus output; hover for the cache reads it leaves out). At the right, once the channel has started, the terminal's output over the last two minutes as a small trace, with its rate per second. The trace only ever shows real output; a chat channel, which has no terminal output, has no trace. When the meter shows the channel's budget instead of its context, it is labelled **Budget**. A Gemini CLI channel shows its tokens today and no context; **—** means nothing has been measured yet.

On tiles 400 px wide or narrower, the topic is hidden and a failed channel's **Open log** moves from the header to the end of its error line, so the state badge stays in view.

A failed channel's error line shows up to three lines and never scrolls: the first line of the error, then the lines of the CLI's last output most likely to be the cause. **Show all** opens the whole message; **Show less** closes it. It ends in a button to a setup page only when the error names one: **Choose project** for a missing folder, **Apply shared rules** when the saved rules are not in the project, **Account setup** for a sign-in problem. A plain exit code has no such button; **Retry** and **Open log** are in the header.

The state badge is a dot and a word, in the state's colour:

| State | Badge | Action |
|---|---|---|
| idle | Idle | **Start** (or Enter on the tile) |
| starting | Starting (pulses) | — |
| working | Working (in the engine's colour) | — |
| waiting | Needs you (frame turns magenta) | **Answer** jumps to the terminal |
| done | Done (blue, from 1.32.1): the agent finished its turn while you were elsewhere; it is still running. Also listed last in **Needs you** as *CHn finished its turn*. Clicking the tile or moving into its terminal clears it. Set by Claude Code terminals (its Stop hook), Codex terminals (from 1.33.2: Codex's own end-of-turn notice, told from its approval requests by their wording), Gemini CLI terminals (agy's status, working then idle or done), and chat channels and Round Tables (the driver's reply) | **Open channel** in Needs you |
| finished | Finished | **Review changes** (G C) |
| failed | Failed (frame turns red) | **Retry** and **Open log** |
| limit | Near limit (context or budget ≥ 80%) | **Write handoff** opens Shared memory |

With the tile focused, Enter starts an idle channel or moves into its terminal.

**Terminal channels** (+ Channel → Terminal) run your login shell (zsh or bash) on macOS and Linux, or Windows PowerShell, in the channel's folder. On Windows, PowerShell runs as administrator through Windows' own sudo when it is on and set to **Inline** (Settings → System → Advanced → **Enable sudo**); Windows asks for approval each time a terminal starts, also when it is started from the phone or another computer. With sudo off, or set to a new window or no input, the terminal runs normally and says how to turn sudo on. They have no model, usage, shared rules check, shared memory or approval alerts, and their output is not saved to session history. They appear on the phone page like any other channel.

**Links in a terminal channel:** hold Ctrl (Cmd on a Mac) and click a web address in the output to open it in the browser; the pointer shows a hint over a link. Only `http` and `https` addresses open, through the host (`flow-open-link`). A plain click does not open a link, so selecting text and a CLI's own mouse use are unchanged. Links in a chat channel open with a plain click.

**Gemini CLI channels** (+ Channel → Gemini CLI, on this computer, another computer's tab and the phone) run Google's Gemini CLI (`agy`) in a terminal. Install it and sign in to it first; **Local engines** shows its version and whether it is signed in. Choose the model in the channel's settings (the list is `agy models`; each name includes its effort) or leave it on Gemini CLI's default. **Permissions:** Ask is read-only from 1.40.1: agy's plan mode (`--mode plan`), which answers and plans but does not change the project, Allow edits is `--mode accept-edits`, Full access is `--dangerously-skip-permissions`. Its questions (trust this folder, approve a command) turn the tile to Needs you. When it ends, Trace keeps the conversation, so the next start continues it, and Session history lists Gemini conversations to resume. Gemini channels have no chat channel of their own, tasks or image paste, and get shared memory and the channel tools through Trace's plugin for Gemini (see Automatic shared memory); its plan limits show in the status bar. **Usage (from 1.28):** Trace reads Gemini CLI's tokens from its own conversation files (`~/.gemini/antigravity-cli/conversations`), so they count in today's total, on the Usage screen and on the phone, by the day they were used. Each Gemini channel and Round Table seat is also counted by itself, from the conversation it writes to: its tokens today show in the Round Table's bar and the status bar, and its runs are listed on Usage with their cost. A seat's count starts when its first request has been written (Gemini CLI writes a request when it ends, and Trace looks every two seconds); until then the bar shows **—**, and 0 means a counted zero. A terminal channel's conversation is found once Gemini CLI has made exactly one new conversation in that folder since the channel started; two Gemini terminals started in the same folder are not told apart, so each shows no count until it quits and names its conversation. These records stay on this computer: other computers' Usage does not list them. Gemini CLI publishes no description of those files: the places Trace reads were matched against what Gemini CLI itself reports, and a record that does not look as expected is skipped, so a change in Gemini CLI can make the count read low until Trace is updated. **Round Table (from 1.28):** Gemini CLI can sit at either kind of Round Table as a seat that reviews or plans (see Round Table seats). A workspace saved by 1.20 with its fixed Gemini seat at a hierarchy table loads without that seat.

**Pasted images:** the CLI attaches the clipboard image itself when it receives its image key: Alt+V on Windows, Ctrl+V on a Mac. On Windows, Ctrl+V pastes like Windows Terminal: text is pasted, and when the clipboard holds only an image Trace sends Alt+V for you. On a Mac, Cmd+V with only an image on the clipboard sends Ctrl+V for you. Alt+V and Ctrl+V still go straight to the CLI. Trace also reads the image and shows it under the terminal as **Attached**, numbered in the order pasted in that run (matching Claude's `[Image #N]` for clipboard pastes). Pressing Enter in the channel moves attached images to a smaller **Sent** row with the time. Click a thumbnail to enlarge it; × removes an attached one from the strip (the agent keeps what it was given). Dropping files on a channel types their paths, quoted when needed, and dropped images are attached too. The strip clears when the channel restarts.

## Chat channels

A **chat** channel runs the agent without its terminal screen, and Trace draws the conversation. **+ Channel** no longer offers Claude chat or Codex chat on their own (on the computer or the phone): a chat comes with a **Round Table** (its leading channel is a chat of the lead seat's agent, Claude Code in the two tables Trace comes with), with **Start in worktree** on a task, or from a linked computer; chat channels you already have keep working. Claude Code runs in its structured mode (`--print --input-format stream-json --output-format stream-json`) instead of its terminal screen, and Trace draws the conversation: your messages with images inline, replies formatted (headings, lists, tables, code), tool calls as cards with their results (edits as before/after), and Claude's thinking folded away. It runs in the channel's folder with the channel's account profile, model, shared rules, shared memory and MCP tools, as a terminal channel does, and usage is recorded the same way.

- On another computer's tab, **Enter** sends a message and **Shift+Enter** starts a new line, as here (from 1.30.3); on a phone Enter stays a new line. The box grows with what is written in both.
- **Permissions** beside the message box sets what the agent may do without asking, at once for a running chat (and for every seat at its Round Table). Choosing **Full access** asks once more, saying what it allows, before it applies (from 1.30.2); **Cancel** keeps the level in effect.
- **A message being written** (its text and images) is kept while you maximise or restore the tile or open another page, and until the channel is removed; it is not saved when Trace closes (from 1.30.2; before, those lost it).
- **While an agent works**, **Stop** stays beside the message box, and **Send** joins it once something is written or attached (from 1.31.2; before, Send took Stop's place). Scrolled up to read, **Latest** goes back to the newest message. A fenced block of code in a reply shows its language and **Copy** above it; headings come in four sizes.
- **Images:** paste, drop or attach (button) up to 10 per message. They go to Claude as images, not file paths. Images over about 5 MB, or in other formats, are redrawn as JPEG at most 2000 px.
- **Approvals:** when Claude asks to use a tool your permission settings do not already allow, a card offers **Allow**, **Allow edits this run** (when Claude suggests it) or **Deny**. An edit's card shows the text it removes and adds (each edit of a MultiEdit), and a new file's its content, scrolled within the card when long (from 1.30.2; before, only the file's name); a command's card shows the whole command (Codex's and Gemini CLI's commands, named Shell, from 1.30.3; before, they were cut at 120 characters). Codex's file-change approvals list the files with their folders (from 1.30.3), not their changes, as Codex sends no more. The buttons follow the seat's agent, not its name: a Codex seat named Reviewer offers **Allow for this session** (from 1.30.3; before, it was offered Claude's **Allow edits this run**). A command's tool card, opened, shows the whole command too. The channel shows as waiting (its tile, the status bar, a notice while its tile is off screen, phone alert) until you answer; **Answer** goes to the card.
- **Stop** interrupts the reply; Claude keeps what it has done. A restarted chat continues the conversation.
- **Codex chat** runs Codex's app server (`codex app-server`, the protocol its IDE extension uses): images go in as images, commands and file changes appear as cards with their output, and Codex's approval requests offer **Allow**, **Allow for this session** or **Deny**. Codex's own settings (approval policy, sandbox) apply as in its terminal.
- Terminal-only screens such as `/config` or the model picker are not part of chat; use a terminal channel for those. On the phone, a chat channel's last 300 events (or 2 MB) of its current run are shown when it is opened, then it follows live; **Conversation** reads the whole transcript.

## Round Table

A Round Table puts you and two or more agents, Claude Code or Codex in any mix, in one conversation. **+ Channel → Round Table** (or **Round Table (hierarchy)**), and the people button beside the message box of a **Claude chat** or **Codex chat** channel, open the setup panel; **Start Round Table** then starts the other agents in the background, in the same folder, and seats them all at a table in the channel you started from. A Round Table is one tile; the other seats have no tile of their own. From a chat, that chat leads the table with its own agent and model. If the conversation was already under way, the leading agent writes a short summary for the newcomers, who also get the latest eight messages.

- **Setup panel:** **Table** lists the two tables Trace comes with (**Claude Code and Codex**, a discussion, and **Planner, builder, reviewer**, a hierarchy) and, under **Yours**, your own; **Kind** switches between a discussion and a hierarchy. The panel opens on the table you last started of that kind. You change a copy of the table you picked. Each seat has an **Agent** (Claude Code or Codex), a **Model** (blank is the CLI's default), a **Name**, **Instructions** of your own (optional, up to 4,000 characters, added to what that seat is told about the table) and, at a discussion, whether it **Edits files**, or, at a hierarchy, its duties. **Add seat** and **Remove seat** change the number of seats (2 to 8); **Rounds** (a discussion's rounds, or a hierarchy's **Review rounds**) is set here too. A seat with no name goes by its agent at a discussion and by what it does at a hierarchy (Builder, Planner, Reviewer, Challenger, Final reviewer); two seats with the same name are numbered. The channel that starts the table keeps its seat, and its agent and model (for a chat, change them in the channel's settings).
- **Your own tables:** **Save as preset** keeps the table under the name you give it, **Update preset** replaces one of yours and **Delete preset** removes it (after asking); the two Trace comes with cannot be changed or deleted, only copied. You can keep up to 20. They are saved in `preferences.json` on this computer and are not synced to other computers. A table already open keeps its seats when you change or delete the preset it came from.
- **Turns:** each message goes to every seat, to discuss first: each says how it would handle it, and nobody changes files yet, the driver included (Trace keeps every seat read-only and declines an edit asked for then). When all have answered, each is shown the others' answers and replies, for up to **Rounds** rounds (0–5, 2 by default). The discussion stops early when all reply `AGREE`. Then the driver alone gets one more turn, shown as **making the changes**: it may edit again, is shown what the others said last, and carries out what you asked with the whole discussion in view (for a question, it gives the answer they reached). Stop, a failed turn or a new message from you ends the discussion without that turn. With **Rounds** at 0 there is no discussion: the driver starts on your message at once and the others answer beside it. Up to 1.28.1 that was so with any number of rounds: the driver began changing files before it had heard the others, and nothing told it to act on what was said. A message sent while they work waits until every seat has finished its turn, then goes to all in place of further rounds; **Stop both** (**Stop all** with more than two seats) ends their turns and sends it at once.
- **Driver and reviewers:** one seat, the driver, edits files; the others are read-only reviewers (Claude Code's plan mode, or Codex's read-only sandbox), and Trace declines any edit they ask for anyway, with a line in the thread. With two seats, **Swap** changes roles without restarting either agent; with more, the **Edits files** list on the bar picks the seat. A Claude reviewer that becomes the driver again returns to the permission mode its own settings started it in; a Codex one returns to `workspace-write`, even if your Codex config uses another sandbox.
- **One thread:** the leading channel shows every seat's messages, each labelled with the seat's name in its agent's colour, with the bar above it: who drives and who reviews, Swap or **Edits files**, **Rounds**, **Seats**, where the discussion is, **Stop both** and **Close**, each seat's tokens today, and how each other seat is doing (running, working, needs approval, stopped). Their approvals appear in the thread, and the tile, status bar and notices show them under the channel's number. **Show** (**Show Codex** or **Show Claude** with two seats) shows one seat's own conversation, with what Trace passed to it.
- **Changing seats later:** **Seats** on the bar opens the panel for the table that is open, or for a saved table that is not open (a seat stopped) while its leading channel runs; the change is then made on the saved table. You can add and remove seats, change names, instructions, models, the seat that edits and the rounds (the channel's own seat cannot be removed, and a table cannot change kind). Trace refuses while the table is working: a discussion must be idle (wait, or press **Stop**). Changing a seat's model restarts that one agent, since a CLI cannot change model while it runs: its conversation is resumed if it had answered before, and the table closes for the moment and seats itself again. Every seat is told about the table again with its next message. A chat can sit at one Round Table only.
- **Haiku at a read-only seat:** Claude Code runs the short model name `haiku` on Sonnet while a seat is read-only (Claude's plan mode; seen with the real CLI on 2026-11-22). For a reviewer or planner on Haiku, type the full name, `claude-haiku-5-5`.
- **Starting, stopping, closing:** the other seats start and stop with the channel, and close with its tile. After a restart, starting the channel starts all of them, and they sit at the table again; a table with a seat missing waits until every seat runs. **Close** on the bar ends the table and stops the other agents. Tables saved by 1.16, where the other agent had its own tile, open as one tile. A table saved by an earlier version (without seats) opens and works as before: Claude Code with Codex, or planner, builder and reviewer.
- **Eight at most:** every seat is a CLI running on this computer, so each counts toward the eight channels Trace runs at once. The panel says how many seats still fit.
- **Gemini CLI seats (from 1.28):** in the setup panel a seat's agent can be **Gemini CLI**, with a model from the list Gemini CLI gives for your account. Up to 1.38 such a seat only reviewed or planned. From 1.39 (the person's decision of 2026-11-24) it takes any seat: it can review, plan, challenge, give the final review, be the discussion seat that edits, build, and lead the table (see **Gemini leading and editing** below). While it reviews or plans, Trace runs it through Gemini CLI's agent protocol (`agy acp`) in its plan mode and declines any file change it asks for; a command it wants to run shows as an approval, as for the other agents, and at **Full access** Trace allows it at once (from 1.29.1; before, a Gemini CLI seat was seated without the table's permissions and passed over when they changed, so it asked before every command whatever the table was set to). From 1.39 its memory tools come from Trace's agy plugin, as for a Gemini terminal; as a chat it takes tasks like any chat (Trace reads TASK COMPLETE from its replies). From 1.39 a seat (or lead) started again picks up its Gemini conversation (`session/load` with the saved conversation ID; before, it started a new one), and its earlier messages show again. Tried with the real Gemini CLI 1.5.14 at both kinds of table (as a reviewer and planner).
- **Gemini leading and editing (1.39):** a table whose lead seat is Gemini (+ Channel → Round Table, Gemini as seat 1, or the builder of a hierarchy) is shown in a **Gemini chat** channel, which stays a chat when the table closes (+ Channel itself still adds Gemini as a terminal). A Gemini seat that edits (the driver, the lead of a discussion by default, or a hierarchy's builder) runs in agy's mode for the table's permission level once it may edit, and in plan mode while it discusses or reviews: **Allow edits** is agy's Accept edits (it edits without asking and asks before commands, each shown as an approval card), **Full access** is agy's Auto and Trace allows whatever it still asks about, and **Ask** is agy's plan mode from 1.40.1: the seat only reads, and a file change it asks for is declined, so a Gemini-led table at Ask discusses but does not edit. A change of level or role reaches agy between turns, and Trace holds the next message until agy reports the new mode. A Gemini chat cannot take tasks (Trace cannot read whether it finished), and a phone shows it as a chat but cannot open a Round Table from it. Checked with unit tests against agy's protocol as agy 1.5.16 answered it (its modes, approvals and `session/load`); a whole table with a real Gemini lead was not run.
- **Custom agents at a table (custom agents, phase 2):** an agent you added whose definition has `acp` is listed in the setup panel's agent list by its name, and takes any seat, as Gemini does. Its seat goes by its name; as a reviewer it runs in its definition's Ask mode and its edits are declined. Saved tables keep which agent sits where.
- **Phone and other computers:** a Round Table is one channel on the phone and in another computer's tab, with every seat in one thread, and an approval any seat waits for shows on that channel. They get the table's state without image data: a waiting message's images arrive as a count, and a hierarchy task's images are left out. A phone allowed to start agents can open one, but only the two-agent discussion table (the other agent joins, the chat's own agent drives first, 2 rounds); it has no **Seats** button, and seats cannot be changed from a phone or from another computer's tab: do that on the computer that runs the table.
- All agents run on your own logins and plans; every message passed between them is used by all. Trace never calls a model itself.

- **Findings:** a reviewer reports each problem on its own line as `FINDING high|medium|low path:line — the problem`, and Trace numbers them F1, F2, …. The driver answers `FIXED F1: …` or `DECLINED F1: …`, and a reviewer checks it with `VERIFIED F1` or `REOPENED F1: …`. Each agent is told, with the others' answers, which findings wait for it. The table bar lists every finding with its evidence, answers, and the files it was reviewed and answered on (a hash of the repository, `repositoryState`). The next round waits until the record is written and the files' state is taken; a finding from a turn during which files changed is marked (the driver works while the reviewer reads). A finding or answer line may sit in a numbered list, a quote or a heading, and may use bold or backticks; marks that belong to the text (`__init__.py`, `` `a.ts` ``) are kept. Keywords and verbs must be in capitals, the severity a whole word, and only a line's first 2,000 characters are read. One answer may name several findings: `FIXED F1, F2, and F3`, `F1 and F2`, `F1/F2`, or a range without spaces (`F1-F3`); a dash with spaces starts the note (`REJECTED C1 — C2 covers this` rejects C1 only), and `F1 F2` names two findings only before a colon, a dash or the end of the line. A line that starts like a review line but cannot be read is named in a notice. When a finding is reopened, the builder's fix prompt shows the reason and its earlier answer. The record, and a message waiting for the agents (published as soon as it is sent, with its images up to 6,000,000 base64 characters; beyond that the bar says how many would be lost), are saved with the table and come back after a restart. A kept message waits for **Send now** or **Drop it**; a new message is refused until then, and Needs you lists it. A message that would make the waiting text longer than 200,000 characters is refused (`TABLE_WAITING_LONG`). Closing a table first saves its review record (every finding, verified ones included) as a note, and each finding not yet verified as an open item, in the channel's memory project. If memory cannot be written, the table stays open and says so; a table closed elsewhere keeps its findings with the channel, and Needs you offers **Save to memory**.

### Hierarchy Round Table

**+ Channel → Round Table (hierarchy)** (or the people button in a chat, with **Kind** set to hierarchy) opens the setup panel. The table Trace comes with, **Planner, builder, reviewer**, seats three agents in the project folder, in one tile: the **builder** (a Claude chat, `claude-opus-5-5` by default, the only seat that edits files), the **planner and final reviewer** (a hidden Claude chat, `claude-fable-5-2` by default, read-only) and the **reviewer** (a hidden Codex chat, `gpt-6.1-sol` by default, read-only), who challenges the plan and later reviews the build. In the panel you can change this: each seat has duties (**Plans**, **Challenges the plan**, **Builds**, **Reviews**, **Final review**) and may be Claude Code or Codex.
- A hierarchy has exactly one builder, and the builder only builds: it is the channel that shows the table and the only seat that edits, so it takes no other duty. It has exactly one planner. It can have any number of challengers and reviewers, and at most one seat for the final review. Challengers, reviewers and the final reviewer are optional: without a final reviewer a task is done when the review rounds end; without reviewers it goes from the build to the final review, or to done when there is none; without challengers the plan is not challenged. The bar leaves out steps nobody takes. Several challengers, or several reviewers, take their step one after another, and the bar says whose turn it is.
- **Review rounds** (1–5, 2 by default) are set in the panel, or on the bar while the table rests. **Seats** on the bar opens the panel for the open table: names and instructions can change whenever the table waits for you (idle, plan waiting for approval, done, needs you, or stopped), but seats can be added or removed, and duties changed, only between tasks (idle or done); it is refused while any seat is working. The builder keeps its seat. Seats that leave may edit again. Changing a seat's model restarts that agent, as at a discussion table.

Trace runs fixed steps (`electron/services/chat/review-chain.ts`) and passes each step's output to the next. Below, "the reviewer" and "Codex" mean the seats that take that step at the built-in table:

1. **Plan:** the planner reads the project and writes numbered steps, files and checks, ending with `PLAN READY`. It runs in Claude Code's plan mode, and its brief tells it to write the plan in its reply, not in a plan file, and not to call `ExitPlanMode` (Trace declines both).
   - **Challenge** (once per task, in any folder): each challenger (Codex at the built-in table), one after another, reads the task and plan (a later challenger is shown the challenges already raised, and told not to raise them again) and reports `CHALLENGE high|medium|low — …` lines (missing requirements, a simpler approach, failure cases), or `NO CHALLENGES`. The planner then answers each, `ACCEPTED Cn` or `REJECTED Cn — why`, and writes the whole plan again, before you see it. A plan you send back is not challenged again; a new task's plan is. A reply with neither stops the table at the challenge: **Continue** asks again, and **Continue without the challenge** shows you the plan as it is.
2. **Approve:** the table waits for you. **Approve plan** starts the builder; anything you write instead goes back to the planner as what to change. What you asked for is kept until the planner writes a plan: **Stop**, a restart or an empty answer from the planner does not lose it (nor the plan before it), and anything you write meanwhile (while the planner works, while it is stopped, or after it answers with nothing) is added to it. The same holds for a follow-up after the final review (below). The bar lists the challenges with the planner's answers. In a tile too short for the whole bar it folds to one line (what is running, who sits at each level, the step's buttons and **Close**); the chevron on that line shows the rest, the challenges included.
3. **Build:** the builder implements the plan and reports what it changed.
4. **Review:** each reviewer in turn reviews the files (a later one is shown the open findings, so it does not report them again) and reports `FINDING` lines, or `NO FINDINGS` on its last line. A reply with neither (and no `VERIFIED`/`REOPENED` answers to earlier findings), such as an empty reply or a question, stops the table at the review; **Continue** runs it again.
5. **Fix:** the builder answers each finding `FIXED` or `DECLINED`; the reviewers check them and look again, for up to the review rounds set (two at the built-in table).
6. **Final review:** the final reviewer (the planner at the built-in table) checks the work against the task, its plan and the findings, and ends with `APPROVED`, or `CHANGES NEEDED:` and what to change. Changes go back to the **Fix** step: the builder makes them, the reviewers review them once more, and the final reviewer reviews again; up to twice, after which the table stops and asks you. Anything you write from here on goes back to the planner as a new plan for you to approve (below).

A task given to the table (from Tasks, or typed) is done only on `APPROVED` (or, at a table with no final reviewer, when the review rounds end); while the plan waits, or the table needs you, the task is marked so and Needs you lists it. A message you write during the steps goes along with the next one, until the final review; the bar says where a waiting message will go. Once the final review is reached (the planner's final review, or the fix and review it sent back), what you write goes back to the planner: it joins the task, the planner writes the plan again from where the work stands (with its plan so far, the builder's report, the open findings and what its final review asked for), the challengers challenge that plan, and you approve it before the builder starts again. This includes a message written during the ordinary review rounds that is still waiting when the final review would start. A message waiting when the planner approves starts as the next task; a message kept from before a restart still waits for **Send now**. If a follow-up would make the task too long (or carry more than ten images), Trace refuses it; if it was already waiting, the table stops at the step it was going to, says why on the bar, and keeps that step and the final review's request: **Drop it**, then **Continue**, goes on as before. A task sent from Tasks while the table works is a task of its own, kept apart from anything you type: it never goes along with a step or into the current task. Up to ten wait, listed on the bar, and they start one per approval, in order, after a message you wrote meanwhile; a message kept from before a restart holds them back until you send or drop it. Tasks waiting are kept through a restart. **Drop it** next to one puts it back in **To do** in Tasks; so does closing the table (here, from a phone or from a linked computer) for every task still waiting. A table that closed because one of its seats stopped keeps them for **Reopen**. While the table waits for you (stopped, or needs you), what you write goes on with the same task: before the final review it goes along with the stopped step when it continues, to the planner with the task if there is no plan yet, and otherwise to the planner as a follow-up, as above. A new task starts once the table is idle or done, or when it comes from Tasks. **Stop** halts the seat at work and **Continue** runs that step again, once the seat has stopped (the bar says **Stopping…** until then); an error stops it the same way (a step Trace itself could not finish says why on the bar), and after a restart the table comes back stopped at its step, with its plan, findings and a kept message. If another seat stops on its own while the builder runs, the table refuses messages and tasks (they would reach the builder alone, unplanned and unreviewed) and offers **Reopen**, which starts it again with the work stopped at its step. A table that would not open again after a restart (the host refused it) says why, in the thread and on the bar; stop the channel and start it again, or close the table. A builder restarted after the workspace folder changed starts in its table's folder, with its seats. A task's own `TASK COMPLETE` instruction is left out of the steps' prompts, since the planner's `APPROVED` decides; each seat may still end with `TASK BLOCKED:` when it needs you. The bar names the seat at work on each step and lists the seats, each with what it is doing and its tokens today. In the thread each message is labelled with its seat's name and what it does there; the planner has its own colour (lime), apart from Claude Code's amber and Codex's cyan. Each seat's model is set in the setup panel (**Seats** on the bar for an open table), used when that seat starts; it must be a model identifier (such as `claude-opus-5-5`) or blank for the CLI's default, and other text ("Opus 5.5") is refused, with the reason under that field. The built-in table's defaults are the planner `claude-fable-5-2`, the builder `claude-opus-5-5` and the Codex reviewer `gpt-6.1-sol`. A hierarchy table saved before 1.26 with a Codex reviewer that has no model starts it on `gpt-6.1-sol` instead of whatever Codex's own settings default to; from 1.26 a blank model is a choice (the CLI's default). A Codex seat of a hierarchy table on `gpt-6-astra` (the reviewer's default before 1.22) starts on `gpt-6.1-sol`, also if Astra is chosen again. Edits by any seat but the builder are declined as at any table.

**Permissions at a hierarchy table** are one setting for every seat: the builder's **Permissions** control sets every other seat too, and a seat that refuses a change sets them all back. A seat added later starts with the leading channel's level and memory project. At **Full access** the read-only seats run commands without an approval card (Claude's plan mode would otherwise ask before each one); their file edits are still declined. At Ask and Allow edits, a read-only seat's command shows an approval card as before. A command a read-only seat runs can still change files: plan mode only stops Claude's own edit tools.

## Tasks

**Tasks** (top bar, or G T) gives an agent a job, optionally limited to some files. **Save and send** types it into the channel.
- **Status:** every task asks the agent to end its reply with `TASK COMPLETE`, or `TASK BLOCKED: <what it needs>` (`shared/task-signal.ts`), as the reply's last line: anything after it, such as a question, means the task is not done. Marks around it are accepted (`#`, `>`, emphasis, backticks, ✅ ✔ ☑ in front, and `.`, `!` or `…` after); a question mark, other words, an unticked `[ ]`, `~~` or a cross are not. Each send gets its own id in the prompt (`Task t-1a2b3c4d: …`), and only replies after that prompt count, so an earlier task's reply, or one with the same title, never finishes this one. When a turn ends (Claude's Stop hook, or a chat reply), Trace reads the reply (a chat's from the conversation, a terminal's from the CLI's transcript, from that task's prompt up to the next task's prompt: the prompt, found up to 256 MB back, and the last 200 messages from at most the 8 MB before the next prompt; at a Round Table, the driver's): `TASK COMPLETE` moves the task to **Ready for review**; `TASK BLOCKED` keeps it in **Working**, waiting for you, with what it needs; any other ending keeps it there marked "not confirmed done". A channel that stops or fails, or a chat turn that ends in an error, leaves it in **Working**, marked, with **Send again**. A Codex terminal that has drawn nothing for 45 s is checked from its transcript the same way; without either line it gets a "may be finished" mark, cleared when it draws again. You can always move a task by hand; a task moved back to **To do** loses its send time and id.
- **Checks:** a passing verification result attached to a task says whether it still describes the task's files. Each run records the commit and the content of every changed file (up to 5,000 files and 256 MB; beyond that it says it cannot tell), and whether they changed while it ran.
- **Everything about this task:** what was asked, channel, folder, branch and commit, changed files, the check, the Round Table findings reported while it was its channel's task, and the pull request chosen for it (**For task** in Changes → Delivery).
- **At a Round Table** a task goes to every seat.
- **Start in worktree** on a To do task (then **Claude chat** or **Codex chat**) creates a `coding-hub/<id>` branch and folder from the committed HEAD (uncommitted changes are not copied), applies the shared rules there, adds a Claude or Codex chat, moves the task to it and sends it. Dependencies are not installed.
- **Needs you** in the status bar, and at the top of the phone's channel list, lists everything waiting for you: approvals with the exact request and how long they have waited, failed channels, channels near a limit, and tasks that stopped (also after Trace restarts), went quiet or are ready for review. On the computer it also lists linked computers' channels that wait or failed (from 1.30.2), and its chip's tooltip names each item. It is the status bar's only alert.

## Approval alerts

When Claude Code or Codex stops to ask for your approval, its tile turns to Needs you, shows the request, and offers **Answer** in its header, which focuses that terminal. You answer the CLI's own prompt; the app never types an answer for you. The alert clears when you type in that terminal, or, for Claude Code, when it reports that a tool finished or its turn ended, so a prompt you answered before the alert arrived does not stay on Needs you.

- **Claude Code 2.1.63 or later:** the app adds HTTP hooks (Notification, PostToolUse and Stop) that report to a local endpoint (127.0.0.1) only the app knows. Tool results sent to it are never read.
- **Codex:** the app turns on its approval notifications and reads them from the terminal output.
- **Gemini CLI 1.4.0 or later:** the app turns on its terminal status (`AGY_CLI_OSC7501=on`) and reads it from the output: waiting for you (with the question), working again, and done.

Older Claude Code versions, `--bare`, or organisation settings that disable hooks leave a tile without alerts.

## Windows installer and updates (v1.2)

The per-user installer creates Start Menu and desktop shortcuts and does not require administrator access. Installed editions provide **Settings → Application updates**, with automatic stable-release checks, explicit downloads, progress, and a confirmed restart. Checks contact GitHub; project contents and terminal output are not sent. Source and portable editions use manual upgrades.

Downloaded updates do not install on ordinary app exit. All local settings, rules, history, and handoffs remain in `~/.coding-hub` across upgrades and uninstall.

A public stable GitHub release with its installer, `latest.yml`, and blockmap is required for live updates. No release has been published by this change. The manual Windows workflow builds and tests a reviewable candidate; [release instructions](windows-releases.md) cover signing and publication.

## Reliability and workflow improvements (v1.2)

- **CLI health:** inspect installed versions, advertised flags, and redacted local authentication status. Fresh discovery validates every launch. Unknown login or model access stays unknown; the app never tests model access through an API or bypasses CLI permissions.
- **Isolated worktrees:** in the channel's settings, choose **Create isolated worktree**. This binds the channel to a unique `coding-hub/<uuid>` branch starting from committed HEAD. Uncommitted changes and untracked files are not copied. Apply shared rules in that folder before starting. Use Git diff with its repository selected, then combine branches through your normal Git review. Settings removes clean, unbound managed worktrees. Its branch is deleted with it only when its commits are already merged elsewhere (`git branch -d`), and so are earlier leftover `coding-hub/` branches no worktree uses; a branch with work of its own is kept. No automatic merges or commits.
- **Recovery:** interrupted processes are marked in history. **Restore launch settings to a channel** creates an idle channel with its recorded repository and parameters; it never revives a PID. A recorded native conversation ID is retained when available; launch/resume still requires Start. With a full workspace, confirmation allows replacing the first idle channel; active channels are preserved. Start the new CLI when ready.
- **Rules validation:** the Shared rules page scans bounded project instruction files, warns about nested/local/override scopes, and offers defined npm `test`, `typecheck`, and `lint` scripts. A native confirmation precedes execution of project code and npm pre/post hooks. Output is capped at 512,000 characters and checks stop after 60 seconds. Semantic conflicts and compliance beyond test coverage cannot be guaranteed.
- **Memory history:** search handoff titles, content, and authors. Revise notes by creating new immutable handoffs linked to their originals. Concurrent revisions coexist. **Inspect Drive conflicts → Keep both versions** preserves both reviewed contents under separate IDs and a backup of the conflicting remote file; stale resolution is rejected. The local folder mirror is tested, while Google Drive owns actual cloud transport.
- **Usage evidence:** each run shows its CLI JSONL source, reported-count label, event count, and configured-price basis. Missing/invalid primary token fields stay unknown. Costs use current exact-model rates and recalculate historical estimates when rates change; they are not billing records.
- **Display and keyboard:** Settings offers 80–125% interface scale, compact/comfortable density, and higher contrast (control outlines at about 9:1, tile frames and the scrollbar thumb at 3:1, and the dimmest marks, such as the idle trace, the drag handle and an offline computer's tab, as readable text; a terminal's own scrollbar is xterm's and does not change). `Alt+1–8` (`Cmd+1–8` on a Mac) focuses channels, `F1` opens help, and `Ctrl/Cmd+Shift+P` opens commands. Visible focus, a skip link, and reduced-motion support improve navigation. Display settings remain in the local Electron profile, separately from synced memory.

## Help and shared rules (v1.1)

**Help & AI guide** provides searchable local articles covering AI agents, models, reasoning, tokens/context, MCP, skills, plugins, hooks, permissions, instruction scope, memory, prompting, review, usage, authentication, Windows setup, and troubleshooting. Search titles and article text, filter by category, and follow related topics. The guide is available offline and can be opened from navigation, the top bar, or the command menu.

**Shared rules** provides one saved rule document for Claude Code and Codex:

1. Open Shared rules and write your expectations, or use the example as a starting point.
2. Select the workspace root, independent channel repositories, and any additional project folders you want to receive them. Previously registered projects are listed too.
3. Choose **Save and apply**. The identical managed section is written into each selected project's `CLAUDE.md` and `AGENTS.md`. Existing text and shared-memory sections are preserved; private backups are created.
4. Restart running channels to load the new instructions. When nonempty shared rules exist, the native host refuses new launches in a folder unless both engine files contain the current saved version. Apply the rules to a new project before starting its channels.

The rule source is local at `~/.coding-hub/shared-rules.json`; it is separate from Drive handoff notes. Updating the rules applies them to selected projects. Unselected projects with an older version must be updated before their next launch through Trace. CLI sessions started outside this app use their own normal instruction discovery.

A registered project whose folder no longer exists is listed with an error and **Remove**, which takes it off the list (`shared-rules.json`) without touching any file. Saving with no projects selected stores the rule draft locally. Clearing the editor and saving removes only the managed rules section from selected projects. Refresh/reload explicitly replaces an unsaved draft. Stale project files and stale saved-rule revisions are rejected rather than overwritten; failed multi-file saves roll back completed replacements when no external edit or file lock prevents restoration.

These rules are real project instructions, not a guarantee of model compliance. Higher-priority engine instructions, nested project files, and CLI permissions still apply. Resolve contradictory instructions and verify results. Tests, hooks, permissions, and CI provide mechanical enforcement when required. Rules do not automatically commit, deploy, or change permission settings.

## Automatic shared memory

Every Claude Code, Codex and Gemini channel started in Trace gets shared project memory automatically, in every project, with no changes to project files. Turn it off in **Settings → Automatic shared memory for every project**.

- **At launch** the channel waits up to 1.5 seconds for its project's Drive sync, so notes another computer wrote moments ago are included (without Drive it starts with the notes here), then reads the notes without holding Trace; channels of one project that start within 30 seconds share that one read. The session receives the project's most recent handoff notes (up to about 6,000 characters and eight notes, labelled as history rather than instructions: notes someone wrote first, newest first, then at most two automatic session summaries in the space left) and the `coding-hub-memory` tools **read_memory** and **write_handoff**. Claude Code gets them through `--append-system-prompt` and `--mcp-config`; Codex through `--config developer_instructions` and `--config mcp_servers.…`. Any `developer_instructions` already set in your Codex configuration are kept and come first.
- **When the session ends** Trace writes a summary note: the files that changed during the session (from `git status`), commits made, and the agent's last message. Sessions that changed no files, made no commits and ended on a message under 200 characters (or none) are skipped, and so are the hidden agents at a Round Table (every seat but the leading channel): the leading channel's summary covers the table. Agents can still write fuller handoffs with **write_handoff**.
- **Project keys are automatic.** Clones and worktrees of the same Git remote share one key on every computer (for example `app-1a2b3c4d5e`); unrelated folders with the same name stay separate. **Shared memory** shows the key for the selected project.
- **Memory tools:** `read_memory` (newest first; `query` returns notes containing every word; `supersededBy` marks replaced notes; `commitStatus` says whether commits a note names are in this clone and on remote branches, as of the last fetch), `write_handoff` (`supersedes` to revise a note, `open_items` for what is still to do, `commits` for commits it made; `author` defaults to the engine Trace started), `list_open_items`, `resolve_open_item`, `list_decisions` and `retire_decision`. Commit ids may be 7 to 64 hex characters (SHA-1 or SHA-256); `read_memory` checks the newest ten commits a note names and says how many more were not checked, and so does **Shared memory**. Codex is started with `default_tools_approval_mode="approve"` for Trace's own memory server only, so chats and Round Table reviewers can use them.
- **Pinned decisions** are notes titled `Decision: …`, retired by a `Retired decision: …` note that supersedes them (`write_handoff` `decisions`, `list_decisions`, `retire_decision`); they come first in the launch notes.
- **Open items** are notes titled `Open item: …`; resolving one writes `Resolved: …` that supersedes it, so every version of Trace and Drive sync handle them. They come first in the launch notes, and **Shared memory** lists them with **Resolve** and a field to add one.
- **Gemini** (the owner's decision of 2026-11-24; checked with agy 1.5.15): agy takes MCP servers only from its own files, so Trace keeps a plugin of its own in `~/.gemini/config/plugins/trace` (`plugin.json`, `mcp_config.json` with a `memory` and a `channels` server, and the rule `rules/AGENTS.md`), written, or pointed at this Trace, before each Gemini launch. Your own `~/.gemini/config/mcp_config.json` is not touched. agy names the servers `trace_memory` and `trace_channels`. Each run's notes folder, key, folder and launch notes go in agy's environment, which agy passes on to the servers. The launch notes come from the `memory_context` tool, which the plugin's rule asks the agent to call before it starts: agy has no appended system prompt, and it keeps a server's MCP instructions in one file for every agy on the computer. At Allow edits the memory tools, and the channel and task tools that only look, run without asking; at Ask, agy asks. An agy started outside Trace starts the same servers, which then offer no tools. The memory key is always the folder's own (a Gemini channel has no **Shared memory project**). `agy plugin disable trace` turns it off: Trace then says so once and starts Gemini channels without memory. A Gemini session's summary has the files changed and commits, not the agent's last message (Trace does not read Gemini's conversation for it). Notes a Gemini channel writes have the author `gemini`; a Trace older than this one leaves them out when it reads notes.
- **A channel's memory project:** **Shared memory project** in a channel's settings picks another project's notes; a Round Table uses the leading chat's. A channel started in the home folder without one raises a notice.
- Applies only to channels started in Trace. For CLIs run from other terminals, or for teammates who clone the repository, use the project installation below. When a project already has `coding-hub-memory` installed, channels use that server instead of adding a second copy. If that entry points at a program that no longer exists (for example after an update moved the app), Trace updates its paths to the current install and says so. If it uses a different memory key from the folder's automatic key, Trace warns, because those channels read and write the other key's notes.

## Channels that keep running after Trace quits

From 1.36.0, in the installed app, terminal channels (Claude Code, Codex and Gemini CLI terminals, and shells) run in a small background part of Trace, the **runner**, instead of inside Trace itself. Quitting Trace, closing it by mistake, a crash or an update no longer stops them: they keep working, and when Trace opens again each one is back in its tile with its screen as it is now, still running ("A channel kept running while Trace was closed"). It works the same however Trace went away.

- **Stopping them.** A channel's own **Stop**, or **Stop all channels and quit** in the tray menu. Plain **Quit Trace** says in the tray that channels keep running. On Windows an update no longer waits for them either. Restarting the computer stops them; **Start channels again when Trace opens** (1.32.0) then starts the agents again on their conversations, as before.
- **What comes back with a channel.** The program itself, with the output it wrote while Trace was closed (the last 1 MB), its approvals ("Needs you"), Done, and channel tools. Trace's hook and channel-tool servers come back on the ports they had, so the agent's own signals still arrive. If another program took a port meanwhile, the screen check (1.35.3) still catches approvals.
- **What does not.** Per-run usage (the Usage page's entry for that run and a session token limit) is not followed again for a channel taken up after a restart; the CLI's own usage logs still have it. The run's saved log has no output written while Trace was closed. Chat channels still stop when Trace quits.
- **Turning it off.** **Settings → Preferences → Keep channels running after Trace quits** (on by default; channels started after saving). Off, channels run inside Trace and stop when it quits, as before 1.36.0. A source run (`npm run dev`) leaves it off unless `CODING_HUB_RUNNER=1`; `CODING_HUB_NO_RUNNER=1` turns it off anywhere.
- **How it works.** [docs/background-runner.md](background-runner.md). The runner runs from its own copy of the files it needs in `~/.coding-hub/runner/kits/` (about 265 MB on Windows, copied once for each version of the runner), never from Trace's install folder, because Trace's Windows installer stops everything running from there before it updates. It listens only to this user (a named pipe or a socket in Trace's storage folder, and a secret in `runner/secret`), runs only what Trace asks it to, and leaves by itself a minute after its last channel ends with Trace closed.

## Plugins from GitHub

From 1.37.0, **Skills & plugins → Trace plugins** installs plugins from GitHub as well as from a folder ([docs/plugins.md](plugins.md)).

- **Install from GitHub:** enter `owner/repo`, or `owner/repo/folder` for a plugin inside a repository, and optionally a branch, tag or commit, then **Preview**. Trace fetches it with this computer's own Git, so a private repository works when Git is signed in to GitHub here (Git Credential Manager, or `gh auth setup-git`); Trace never sees a token.
- **The preview** shows the exact commit, what the plugin may ask Trace to do, every command it may run, and its files. Nothing runs before **Install**, and a system dialog asks once more. Then its build steps run (at most 10 minutes each, shown in its runs) and it is turned on.
- **Updates:** Trace checks once a day where each GitHub plugin's branch or tag is (**Check for updates** asks now) and shows **Update to …** on that plugin. It never updates by itself. The update preview says what changes: commands added or removed, and new permissions. The version before is kept for any of its programs still running, and older versions are removed.
- **Browse** lists GitHub repositories with the topic `trace-plugin` (GitHub's public search, kept an hour). Nobody reviews this list; **Preview** goes through the same steps.
- **Remove** stops the plugin and deletes its versions; its `data` folder stays unless removed too.

## Channel tools

**Settings → Preferences → Let agents see and message other channels** (from 1.33.0, off by default, per computer). When on, each Claude Code and Codex channel started afterwards gets four tools from Trace's `trace-channels` MCP server:

- **list_channels**: this computer's channels (a Round Table counts as its lead's channel): number, name, CLI, whether it runs, the approval it waits for, its folder, and which one is the caller's.
- **read_channel**: another channel's last replies (1 to 20, from its CLI's own conversation; none for terminals or Gemini CLI).
- **send_to_channel**: types a message into another channel as you would, starting *[Message from CHn (name): an agent, not the person]*. Refused for the caller's own channel, a stopped one, and one waiting for you to answer an approval (its Enter would answer it). A chat gets it as a chat message (from 1.33.2, at a Round Table the whole table gets it, as a message typed there does), a terminal as a line.
- **wait_for_channel**: waits until another channel's turn ends (Claude Code's end-of-turn hook, or a chat turn), it asks for an approval, or it stops, up to 30 minutes; says which.

Claude Code asks your permission for each tool as it does for any MCP tool, unless the channel runs at Full access. Codex takes the three that only look (list, read, wait) without asking (from 1.33.2), and asks before **send_to_channel**; a Codex chat, which has no such prompt, therefore refuses to send but can list, read and wait. Turning the setting off stops them at once, even in running channels. Each run reaches Trace through its own secret address on 127.0.0.1, which also tells Trace which channel is asking. Gemini channels get them through Trace's plugin for Gemini (see Automatic shared memory): at Allow edits the ones that only look (list, read, wait, list_tasks) run without asking; otherwise agy asks.

### Task tools

**Settings → Preferences → Let agents read and update Tasks** (on by default, per computer, separate from the channel tools). When on, each Claude Code and Codex channel started afterwards gets three more tools from the same `trace-channels` server (either setting adds the server; it lists only the tools whose setting is on):

- **list_tasks**: the Tasks board's tasks for the project the channel works in (tasks whose folder is the channel's folder or contains it), optionally one status (`queued`, `active`, `review`, `done`): id, title, details, status, notes.
- **add_task**: a task in To do, in the channel's folder, with title (up to 150 characters) and details (up to 2,000). Its notes say *Added by the agent in CHn (name).* It goes to no channel until you send it.
- **update_task**: moves one of the project's tasks to Working (`active`) or Ready for review (`review`), adds a note (up to 1,000 characters) on a line of its own signed *CHn:*, or both. Refused: moving a task to Done or out of Done, a task in another project (it reads as missing), and a note that would take the task's notes past 2,000 characters.

Only you move a task to Done, remove a task, or change its title, details, files, channel or check: there are no tools for those. The Tasks board shows an agent's change at once. Codex takes **list_tasks** without asking and asks before **add_task** and **update_task** (so a Codex chat can list but not change tasks); Claude Code asks for each, unless the channel runs at Full access. Turning the setting off stops them at once, even in running channels.

## Trace plugins

**Agent setup → Skills & plugins → Trace plugins** (from 1.35.0; the design is in [plugins.md](plugins.md)). A plugin is a folder with a `trace-plugin.json` manifest and the programs it names, in any language. It runs as you, without a shell and without a sandbox, and nobody reviews it.

- **Link a folder** adds one from a folder on this computer, after a system dialog shows every command it may run and what it may ask Trace to do. It is read in place, so changes to it count from the next run. (Installing from GitHub, updates and a list to browse come in later versions.)
- **Actions** are in the command menu as *plugin name: action*: for the workspace always; a channel's, when the menu was opened from that channel's terminal; a repository's, on Changes. An action runs for up to five minutes.
- **Events**: a plugin's commands run when a channel needs you, ends its turn, fails, starts or stops (`channel.needs-you`, `channel.turn-ended`, `channel.failed`, `channel.started`, `channel.stopped`), when a task is ready for review, a worktree is made, or Trace starts. Each runs for up to 30 seconds, at most once per channel every 10 seconds.
- **What it is told:** `TRACE_EVENT`, `TRACE_PROJECT`, `TRACE_CHANNEL`, `TRACE_CHANNEL_NAME`, `TRACE_FOLDER`, `TRACE_BRANCH` (actions), `TRACE_MESSAGE`, its own data folder `TRACE_PLUGIN_DATA` (kept across updates), and `TRACE_API_URL` and `TRACE_CLI` for the plugin API.
- **The plugin API:** `trace channels.list`, `channels.read`, `channels.wait`, `channels.send`, `channels.start`, `channels.stop`, `channels.add`, `tasks.list`, `tasks.add` and `notify`, each allowed only with the permission the manifest declares (`channels.read`, `channels.send`, `channels.control`, `tasks`, `notify`). A message it sends is marked as from the plugin; a channel waiting for your approval is not sent to. `TRACE_CLI` is a small launcher (`trace.cmd` on Windows, which a program starts through its shell).
- **A command's program** is a path inside the plugin's folder or a program on PATH (npm, pnpm, yarn and npx through their Node scripts). A `.js` file runs with Node. A Windows `.cmd` or `.bat` is refused, since it starts only through a shell.
- **Runs:** each plugin shows its last run; **Runs** lists this session's last 50 with the end of their output. A failed run raises a desktop alert. **On** turns a plugin off, which stops its programs and its API address at once; **Remove** forgets it (a linked folder stays where it is).
- Kept in `plugins/installed.json` in Trace's storage folder, per computer.

## Event hooks

**Settings → Event hooks** (from 1.33.1): a program of your own that Trace runs when a channel needs you, ends its turn (Claude Code's end-of-turn hook or a chat turn; at a Round Table, its lead's), or fails. Give its full path and its arguments, one per line. Trace asks in a system dialog with the exact command before saving it, so nothing in the window alone can add one. It runs as you, without a shell, with `TRACE_EVENT` (`needs-you`, `turn-ended`, `failed`, or `test`), `TRACE_CHANNEL` (the number), `TRACE_CHANNEL_NAME`, `TRACE_FOLDER` and `TRACE_MESSAGE` set, and is stopped after 30 seconds. One hook runs at most once every 10 seconds for a channel, and at most four run at once. **Test** runs it once now; each hook shows how its last run went. Hooks are kept in `event-hooks.json` in Trace's storage folder (per computer).

**Verification profiles from the command menu** (from 1.33.1): each profile is an action, *Run verification: name*, which opens Verification profiles and runs it there after its usual confirmation.

## Shared Google Drive memory

On Windows the default shared folder is **`G:\My Drive\Coding Hub`**; on a Mac there is no default, so choose the folder Google Drive for desktop keeps there. The `CODING_HUB_DEFAULT_DRIVE_DIR` environment variable, set before Trace starts, replaces that default on Windows and on a Mac (an empty value means no folder) until preferences are first saved (`preferences.json`). Saving preferences stores the folder the Settings field shows, and the variable is not read after that. Trace's own tests set it so they never write into a real Drive folder. When the folder can't be used (none chosen, not a full path on this computer, or missing), Memory and Settings → Sync between computers say why, with Drive folder ID `1X057crI-PHRV3ie1tl5btF4bUbuhxzwM` retained as a reference. Google Drive for desktop handles authentication and cloud upload; no separate OAuth credentials are required by Trace.

1. Confirm **Settings → Local Drive folder** points to the actual synced/mounted folder. Save preferences if you change it.
2. Open your project, then open **Shared memory**. Use the same **shared project key** on every desktop participating in that project's handoffs. Different project keys keep notes separate.
3. Optional (automatic memory covers channels started in Trace): use **Enable memory for both CLIs** and review the changes, then **Install local memory server**. It uses the folder's automatic memory key when one is available, so terminal sessions and channels started in Trace share notes. This adds a `coding-hub-memory` entry to project `.mcp.json` and `.codex/config.toml`, and appends marked instructions to `CLAUDE.md` and `AGENTS.md`. Existing files receive private backups. Existing server entries with that name are never silently replaced.

**Near the context limit.** When a Claude Code or Codex channel has used 80% of its context window, Trace asks the agent to save a handoff with `write_handoff` once its turn ends (`src/runtime/auto-handoff.ts`). It asks once each time the context climbs to the limit (compacting brings it down; the next climb asks again), and not while the channel waits for an approval, at a Round Table, in a terminal or Gemini CLI channel, or with automatic memory off. The request shows in the channel like a message you typed. **Write handoff** on the tile still opens Memory to write one yourself. Once the agent's handoff is in the project's memory, a terminal channel is compacted (`/compact`) when that turn ends; a chat channel is not, and neither is a channel whose agent saved nothing.
4. Restart the channels, and any CLI sessions in other terminals. Approve the MCP server / project trust through the CLI's normal controls. The local server exposes **read_memory** and **write_handoff**.
5. Save a manual handoff or ask the agent to record its decisions, changed files, checks, remaining work, and blockers. The next agent can read those notes through MCP.

Notes are stored locally at `~/.coding-hub/memory/<project-key>/<uuid>.json` and mirrored into `G:\My Drive\Coding Hub\AI-Coding-Hub-Memory\<project-key>\`. Sync is additive and retries every 30 seconds for projects opened in the app; **Sync now** gives an explicit result, and pressed while a sync runs, it waits for that one. Syncing never holds Trace's window or terminals: Drive answers each file slowly, so every read and copy runs in the background, one sync per project at a time. Starting a channel waits up to 1.5 seconds for its project's sync, so notes written on another computer seconds earlier are usually in its starting context; saving a note does not wait for Drive. A note with the same size in both folders is taken as the same note and not read. A note whose copies differ in size is read on both sides once; when they hold the same note, the pair is remembered in `memory/.drive-compared.json`, which is only a cache (delete it and Trace compares those notes once more). If Drive is offline, notes remain local and sync later. Conflicting note IDs preserve both files and require review; one conflicting or unreadable note no longer stops the project's other notes from syncing. A project found above its note limit is brought back under it by its next note, which moves the oldest handoffs to `archive/` (open items and decisions are never moved). Google Drive may create its own conflict copies; these are not silently merged.

The app reports folder synchronization, not Google's cloud upload completion. Check Drive for desktop's own status when moving between machines. The existing Drive folder URL is a reference; the app uses the local folder, not a website connector. Terminal logs, SQLite databases, and credentials do not sync. Conversations are not automatically copied between agents; curated notes are read as project data. The memory server uses the app's current executable and compiled source paths; reinstall its project entries if you move the app directory or switch to a packaged executable.

## Sync between computers

Turn on **Settings → Sync settings, rules, templates and usage between computers** on each computer, with the same Drive folder. Every 30 seconds (or with **Sync now**) Trace exchanges these through `AI-Coding-Hub-Sync\` in that folder:

| Item | How it merges |
|---|---|
| Settings (your own price rates, terminal font size and rendering, automatic memory) | A change on one computer is taken by the others. The Drive folder and the sync switch stay per computer. |

Every computer must use the **same** Drive folder. Two computers set to different folders of one Drive (`My Drive` on one, `My Drive/Coding Hub` on another) each sync into their own `AI-Coding-Hub-Sync` and share nothing, without an error. Trace looks at the folder above its Drive folder and the folders in it every few minutes, and **Settings → Sync between computers** says when other computers sync through one of them, with **Use the same folder** on the computer that should move (the one with fewer computers on its folder; the others are told to do it there). Moving adds this computer's notes and usage to that folder; nothing is removed from the old one. From 1.27 the computer that should move does so by itself, once per folder, tells you with a notification, and shows **Move back** under Settings → Sync between computers; a computer you moved back is not moved again.
| Shared rules (the text) | Same as settings. Rules that arrive from another computer are saved but not applied to this computer's projects; Shared rules says where they came from, and those projects' channels do not start until you apply them. |
| Project templates | Merged as a set; deleting one deletes it everywhere. |
| Usage history | Each computer writes only its own file. Usage shows other computers' sessions with the computer's name; the status bar's today total counts this computer only. |
| Custom agents (`agents/<id>.json`) | One file per agent. A change on one computer is taken by the others; when both changed one, a change wins over a removal, else the newer one wins (the replaced definition stays in `config-backups/`). A definition that arrives is **Off** on that computer: the Agents page says "Added from your other computer (name). Check it, then turn it on.", and **Turn on** shows the system dialog. Which agents are turned on (`agents-confirmed.json`) never syncs. |

If settings or rules change on two computers before they sync, nothing is overwritten: **Settings → Sync between computers** shows the conflict and lets you keep this computer's version or take the other one. Running channels, recorded output, the project list, verification profiles and account sign-ins stay on each computer. So do Claude Code, Codex and Gemini conversations: each CLI keeps them in its own folder on that computer, filed under the project's path there, so Session history lists only this computer's and Resume continues only those. Another computer's are listed, and resumed there, with **History** on its tab (Other computers, below). Usage records include project folder paths, so they are visible to anyone with access to the Drive folder.
## Phone access

Read and type into running channels from your phone, including answering approval prompts. It is off until you turn it on in **Settings → Phone access**.

1. **Install Tailscale** on this computer and your phone (tailscale.com/download), signed in to the same account. Tailscale is a private network between your own devices; nothing is opened to the internet.
2. **Set up Tailscale HTTPS.** Trace asks for confirmation, then runs `tailscale serve --bg --https=443 http://127.0.0.1:47821`. Your tailnet must have HTTPS certificates turned on (Tailscale admin console → DNS). If they are off, or Tailscale wants Serve approved, the card shows the steps, opens the Tailscale page, and tries again by itself when you come back to Trace. Remove it later with `tailscale serve reset`.
3. **Pair a phone.** Scan the QR code with the phone's camera, or open the address shown and type the code. A code works once, for five minutes and ten tries.

On the phone:

- **Add it to your home screen** (Share → Add to Home Screen on iPhone, or Install app on Android) so it opens like an app.
- **Channels** lists every channel with its state; one that needs you is outlined and shows the request.
- **A terminal channel** opens at the phone's size: the computer redraws its CLI for the phone (like tmux), even while you use the computer, and the text is at the size you chose. From 1.35.2 a channel is drawn at the size of whoever last used it (herdr's rule): the desktop's size comes back when you type in that channel's tile at the computer or click into it, when you leave the channel on the phone, when you lock the phone or switch apps (coming back to Trace takes the phone's size again), and when the phone disconnects. Typing or touching the channel on the phone counts as using it, so a phone you are working on keeps its size. Once the computer has taken the channel back, the phone takes its size again only when you touch the channel (its screen, keys or message box), change the text size or open the channel again, not when it reconnects, wakes or its screen turns (from 1.36.0, coming back to the app also waits for a touch). Meanwhile the phone shows the computer's wider screen at your text size, to swipe sideways, with a line saying a touch brings it back; it never shrinks the text to fit (**Desktop size** and **Fit to phone** were removed in 1.36.0). **A− / A+** change the text size, and so how much fits. A chat channel is not resized. A channel on another linked computer, reached through this one, keeps the earlier rule there: it is redrawn for the phone once that computer has had no keyboard or mouse input for two minutes.
- **Scroll** by swiping up or down over the channel. **Copy** opens the channel's text, where you can press and hold to select part of it, or **Copy all**. Tap the terminal to open the message box, use the keys (Enter, Esc, Ctrl C, ↑, ↓ always; **More** adds Tab, ⇧Tab, ⌫, ←, →, 1–3, y, n, Copy, Conversation and A− / A+, and stays open or closed as you leave it) for prompts, or type a line and press **Send**. **☰** in a channel's header lists every channel, those that need you first (with their count on the button), to switch in one tap. While no computer answers, the last screen stays, dimmed, and typing waits until it is back. A phone that falls behind a busy channel gets the screen as it is once it catches up, instead of a backlog of old output.
- **Channel settings** (the sliders button in a channel's header, on a phone with **Can start and stop agents** on, for this computer's own channels): the channel's name and, for an agent, **Permissions** (Ask, Allow edits, Full access), its **Model**, chosen by name from Claude Code's current models or from what Codex or Gemini CLI lists for your account, and Codex's **Reasoning effort**. Permissions reach a running chat at once (and every seat at its Round Table) and a terminal channel at its next start; the model and effort are saved only while the channel is stopped, as on its tile. The Claude account, folder, budgets and token limits are changed on the computer.
- A restarted channel starts its screen afresh. **Conversation** in a Claude Code, Codex or Gemini channel shows its whole conversation from the CLI's own transcript (Gemini's without what its tools printed), including what was said before restarts, also for channels on linked computers.
- **Screen** at the top of the channel list shows the computer's screen and controls it: tap to click, drag to move, type in the field under it, with keys for Esc, Tab, Return, Backspace and the arrows. Above it: **Display** (a Windows computer with more than one: all side by side, or one at full size; the phone asks /api/phone-screen-displays, since a browser cannot read the WebSocket's answer), **Actual size** (the picture unscaled: a drag moves around it and a tap still clicks) and **View only** (taps and keys go nowhere). It goes through that computer's own screen-sharing server, relayed by Trace over the same remote: on a Mac, macOS **Screen Sharing** (turned on once there), which asks for its user name and password (they go to the Mac, not Trace); on Windows, Trace's screen service, when **Share this screen** is on there, which lets in a phone with **Can start and stop agents** on (Settings → Phone access, off by default; turning it off closes the phone's open screen), with no other password (the phone is named by the clock while it watches, and replaces any other viewer). The phone opens it with a one-time ticket (30 seconds, one use), at most two at once. A locked Mac shows black and takes no keys. When the screen cannot be opened, the phone says why (for example that the computer could not capture its screen). The phone uses /api/phone-screen-ticket and /api/phone-screen, since a Windows computer that shares its screen passes /api/screen to its screen service.
- **Remove this phone** at the bottom of the list unpairs it.
- **Chat channels** (Claude chat, Codex chat) are the conversation itself, as on the computer: messages, tool cards, approvals, photos from the camera or library, Stop, and a Round Table's bar. What you send from the phone also shows on the computer.
- **Tabs along the bottom:** **Usage** (today's tokens and cost, the daily budget, and each account's plan limits), **Tasks** (the task board), **History** (conversations to resume), and **More** (memory handoffs for this computer's projects, with **Leave a handoff**, and the computer's screen).
- **Can start and stop agents** (Settings → Phone access, per phone, off by default) lets that phone start, stop, restart and add channels (**+**), move tasks, resume conversations and open a Round Table. Without it, those controls do not show, and the computer refuses them.
- **Updates:** the phone app is saved on the phone. After Trace is updated on its computer, the app reloads itself for the new version once nothing is open in it (a channel, the screen, a sheet or an unsent message), once per version.
- **Alerts:** **Turn on alerts** under the channel list, and the phone gets a notification when a channel needs you or stops with an error, even with Trace closed. Tapping it opens that channel. On iPhone and iPad this works once Trace is added to the Home Screen and opened from there (iOS 16.4 or later). Settings on the computer shows which phones have alerts on and can **Send test alert**.

Alerts use Web Push. Trace encrypts each alert on the computer for that phone only (RFC 8291) and signs the request with a key of its own (VAPID, `remote-push.json`); the browser's push service (Google, Apple, Mozilla or Microsoft) carries it but cannot read it. The computer only ever sends to those push services, at most one alert per channel every 20 seconds.

How it is protected:

- Trace listens only on this computer (`127.0.0.1:47821`); the phone reaches it through Tailscale, which encrypts the connection and admits only your devices.
- Every request also needs the key a phone received when it paired. Only a hash of each key is stored (`remote-devices.json`), and **Remove** in Settings locks a phone out at once. Turning phone access off closes the listener.
- Requests must name this computer or its tailnet address, and Tailscale Funnel (public internet) requests are refused.
- A paired phone can read channel output and type into channels that are already running, the same as typing at the desktop, and use chat channels: send messages (up to 10 images), answer approvals, interrupt, and take part in a Round Table. It can also leave handoff notes in shared memory and ask for a coaching review. It cannot start, stop, close or add channels unless **Can start and stop agents** is turned on for that phone in **Settings → Phone access** (off by default; it also lets the phone open a Round Table). It cannot reconfigure channels or reach any other part of Trace, except **Screen**, which still needs the computer's own sign-in. Treat a paired phone like an unlocked keyboard on this computer, and remove phones you no longer use.

## Other computers

Trace on each of your computers can link to the others and show their channels.

- **Finding each other.** With sync between computers on, each computer writes its phone remote's tailnet address (never a key) to `AI-Coding-Hub-Sync/computers/<machine id>.json` in the Drive folder. **Settings → Other computers** lists the others. Only `https://<name>.ts.net` addresses are used, so a record in Drive cannot send a code or key anywhere else.
- **Linking automatically.** With **Link my computers automatically** on (the default) on both, computers signed in to the same Tailscale account link without a code; shared and tagged devices still need one. A computer that links this way gets the same key a code gives, so Trace shows a notification each time ("A computer linked to Trace here"; clicking it opens that computer's tab). If it isn't yours, remove it under **Settings → Other computers**. A computer you remove there is kept in `remote-unlinked.json` and does not link itself again until it is linked with a code. That list matches the computer's own id, so it stops Trace on that computer, not a program that makes up a new id; the notification is what shows that case.
- **Linking.** **Show link code** on the computer to be reached gives a code for computers (five minutes, one use). The code decides what is created: a computer code gives a key that may also start, stop and restart channels; a phone's code cannot link a computer. The key is kept in `linked-computers.json` in this computer's data folder, and the other computer stores only its hash. **Unlink** removes it on both computers; the other computer can also **Remove** it.
- **Alerts:** when one of another computer's channels starts waiting for you or stops with an error, Trace shows a notification if its window is not in front (clicking it opens that computer's tab), and the status bar's **Needs you** lists it (**Answer** or **Open channel** opens that computer's tab). Failures are reported by Trace 1.15 or later there. This computer's own channels notify the same way; **Settings → Alerts and daily budget → Desktop notifications** turns all of them off.
- **Daily budget and plan limits:** in **Settings → Alerts and daily budget**, a daily token budget and a daily cost budget (new tokens and estimated cost on this computer, as **Today** in the status bar counts them), and the share to warn at (80% unless changed; from 50 to 99). The numbers are kept to their ranges when you leave the field or save, not while you type (from 1.30.3; before, typing 75 or 0.5 was turned into 50 or 0.01 at the first digit). Trace checks every minute and notifies once at that share and once when a budget is used up, even while it is in front; **Today** in the status bar turns amber, then red. Claude's and Codex's own session and weekly limits (as the status bar shows them) are warned about the same way, once per window (a Claude window is told apart by its reset time to the nearest hour, so different wording of the same reset does not warn again; one with no reset time, by day). What was said is kept in `usage-alerts.json`, so a restart does not repeat it.
- **Update:** **Update** on another computer's tab installs the latest Trace there and restarts it, after you confirm, once its channels are stopped. A copy that updates itself (Windows, or a Mac signed with Trace's Developer ID) uses its own updater; a Mac copy that cannot downloads the new version, checks it, swaps it in and waits until it answers on port 47821, and puts the old version back if it does not within two minutes (log: `/tmp/trace-update.log`). It needs Trace 1.15 or later there.
- **What a linked computer can do:** follow every channel's output (one stream), type and paste text into channels (sent in order, in pieces of up to 4,096 characters; if one piece fails, what was typed after it is not sent, and the reason shows above that computer's channels until you dismiss it), add channels (**+ Channel** on that computer's tab adds a Terminal, Claude Code or Codex channel there, in its own workspace; chat channels are added only on the computer itself), and start, stop, restart or close them (**Close** asks first, stops the channel if it runs, and keeps that computer's last channel). The desktop window on the computer that runs a channel carries the request out, as its own buttons would. If that window is closed, the request is refused.
- **Reconnecting** (from 1.35.1, after herdr's rules): when this computer wakes from sleep, every link connects again at once. A link with no ping for 30 seconds is taken as dead (Trace pings every 10 seconds; one before 1.35.1, every 25). Retries wait 2 seconds, doubling to 30; the wait starts again from 2 seconds only after a connection held for a minute, so a link that keeps dropping backs off. Before, a link could stay dead after sleep for up to a minute, then retried every 2 seconds even while it kept failing.
- **The tab.** Each linked computer gets a tab after the main views. A channel that stopped with an error there shows as **Failed**, with why (from 1.31.1; before, as Idle). New channels stand two to a row until you move them, and a last one alone in its row takes the whole width. While it is open, each tile tells that computer its size, and that computer draws the channel at it once you type into the tile here; clicking into the channel's own tile there, or a phone using it, takes it back (from 1.35.2: whoever last used a channel leads). Merely showing the tile, or the computer being idle, changes nothing, so a channel no longer shrinks while someone only reads it. Otherwise the terminal keeps the other computer's columns and rows and scrolls. Ctrl+V pastes text, as in channels here. An image pasted into a Claude Code or Codex channel there (Ctrl+V on Windows; ⌘V or Ctrl+V on a Mac) is sent to that computer, which puts it on its own clipboard and presses the CLI's image key, as a paste there would; it replaces what was on that computer's clipboard. PNG and JPEG, up to 15 MB; it needs 1.12.1 or later on both. A count on the tab shows channels there that need you. Tiles move by their grip and resize by their corner; the arrangement is kept on this computer, per linked computer, and leaves that computer's own layout as it is. **Conversation** on a Claude Code or Codex tile shows that channel's whole conversation, including what was said before restarts.
- **History** (1.42.0) on a linked computer's tab lists that computer's Claude Code, Codex and Gemini conversations (the 100 newest, as its phones' History shows them), with a filter by title, folder or agent. **Resume** continues one there: that computer adds it as a new channel in its own workspace, which shows on its tab here, ready to start. The conversation stays on that computer; nothing is copied to this one. It needs Trace's window open there, and works with Trace 1.16 or later there.
- **Screen.** **Screen** on a linked computer's tab shows that computer's screen and lets you control it, through its own screen-sharing server (macOS **Screen Sharing**, port 5900) rather than through Trace, so it also works while Trace is closed there. Turn it on once on the Mac: **System Settings → General → Sharing → Screen Sharing**. Trace connects only to a linked computer's `<name>.ts.net` address, over Tailscale. Sign in as a user on that Mac; **Save on this computer** keeps the password encrypted by the system (Windows DPAPI, the macOS Keychain) in `screen-sharing.json`, and **Forget password** removes it. **Control** switches to **View only**, which sends nothing. **Ctrl as ⌘** (on by default on Windows, where the Windows key can't be sent) sends Ctrl as Command, so Ctrl+C, Ctrl+V and Ctrl+Tab do what a Mac expects; Ctrl+V first copies this computer's text to the Mac. Between two Windows PCs (Ctrl+V) or two Macs (⌘V) the paste key hands this computer's text over first too (from 1.31.1; before, it pasted what was on the other computer's own clipboard). Text copied on the Mac reaches this computer's clipboard. While you type into the screen, Trace's own shortcuts (F1, Ctrl+Shift+F, Ctrl+Shift+P, Alt+1–8, the G letters) go to that computer instead (from 1.31.1; before, Trace took them and its page change closed the screen). **Channels** goes back to the tiles and closes the connection. A screen that was showing and drops connects again by itself (**Reconnecting…**), after 1, 3 and 6 seconds; if all three fail, it shows **Disconnected** and why, and waits for **Reconnect**. The count starts again once it has stayed connected for 30 seconds. A first connection that fails, or a refused sign-in, is not retried. **A locked Mac** sends its screen black to viewers other than Apple's, so when Trace there says it is locked (asked every 5 seconds over the link), the screen shows **…is locked** with a password field. When Trace there cannot say (it is closed, or older than 1.13.1), **Unlock** in the bar opens the same field. **Wake and unlock** taps Shift to wake it and bring up its password field, types the password there and presses Return, then checks again; **Use saved password** uses the saved sign-in, which is the same password. Nothing about the password is sent to Trace on the Mac: it goes as keystrokes through Screen Sharing, like typing it there.
- **Updating together.** After this computer has updated to a newer Trace, it asks each linked computer that is on to update too, as **Update** on its tab does. A computer with anything running refuses; it is asked again every half hour for six hours.
- **Sharing a Windows screen.** Windows has no screen-sharing server, so Trace provides one: **Settings → Other computers → Share this screen** (Windows only, off by default) lets linked computers see and control this screen with **Screen**, also while Trace is closed. It starts a background service (Trace run with `--screen-service`, about 100 MB while someone watches), registers it to start when you sign in (**Trace screen sharing** under Settings → Apps → Startup), and has `tailscale serve` pass `https://<name>.ts.net/api/screen` to it on port 47822, which listens on this computer only. A linked computer signs in with the key it was linked with; a phone comes through Trace's phone access, and only with **Can start and stop agents** on for it (Trace signs in for it with its own key, in `screen-service-local.json`, after checking the phone's one-time ticket), and a phone's own key is refused; and **Remove** under Other computers locks that computer out at once. One viewer at a time. While someone watches, a Trace icon by the clock names them and has **Disconnect**. When Trace starts, and when the setting changes, it asks the service to capture the screen once (nobody is shown as watching); if it cannot, Trace says why in the window, as a notification and under **Share this screen**. An update replaces Trace's files while the service runs: the ordinary service is closed by the update and started again, and the administrator one, which an update cannot close, is replaced by Trace when it starts (it ends and runs the service's task again, without asking); from 1.27 the service also makes way by itself once it sees a newer version installed and nobody is watching. Before 1.27 an administrator service stayed on the old version after an update, still answered, and refused every viewer. Every display is sent as one picture, arranged as in Windows' display settings (one display scaled to 1920×1200 at most; several to 3840 wide and about two 1920×1200 screens' worth of pixels at most), as JPEG, only the parts that change, sent again sharper once the screen has been still for 0.4 s (so text that stays put is crisp); at most two updates are on their way at once, each confirmed by the viewer (an RFB fence), so a slow link gets fewer, newer pictures rather than a queue of old ones. With several displays, **Display** in the bar shows one of them on its own (numbered from the left) at the size one display gets, or all of them again; clicks map onto whichever display they land on (SendInput's virtual-desktop coordinates); keys and the mouse are pressed through Windows PowerShell, which every Windows has, so nothing else is installed; it starts when the viewer connects, so the first clicks are not held up. If the capture stops (a display's capture ends, or it fails) or the displays change (one added or removed, or a resolution or scaling change), the session ends and the viewer connects again to a capture of the new layout. On a Mac viewing it, **⌘ as Ctrl** (on by default) sends ⌘ as Ctrl, so ⌘C and ⌘V copy and paste. If the capture does not start within 20 seconds, the viewer is told so (rather than that sharing is off) and can **Reconnect**; turning **Share this screen** off and on restarts the service. If the service stops on an error, it starts itself again (unless that happens within a minute of starting), and Trace, while open, checks every minute and starts it again if it has gone. Limits: the computer must be on, awake, signed in and unlocked (while Trace there is open, the viewer says when it is locked: Windows takes no keys or clicks from other programs at its lock screen, so it must be unlocked at the computer); apps running as administrator can be controlled only with **Also control apps running as administrator** (below); the clipboard carries text only: any text with Trace's viewer (noVNC's extended clipboard), Latin-1 with other VNC viewers. **Also control apps running as administrator** (under Share this screen) runs a second, small part of the service as administrator, which only presses the keys and moves the mouse: Windows asks permission once (an administrator account is needed) to register a scheduled task, **Trace screen sharing (administrator)**, which starts it with the highest rights when you sign in (and up to three more times if it fails), beside the sign-in entry that starts the service itself; Trace starts that task without asking. The service still captures the screen and serves the viewer with your own rights, and sends the viewer's input to that part on this computer only (port 47823, with Trace's own key); if that part is not running, the service presses the keys itself, so everything but apps running as administrator is still controlled, and Trace says so under **Share this screen**. Up to 1.28.0 the task ran the whole service as administrator instead, and nothing could be viewed with the option on ("could not capture its screen: Could not start video source"): from Windows 11 24H2, Chromium captures the screen only through Windows Graphics Capture, which answers an administrator Electron "access denied". 1.28.1 uses the same task, so updating asks no permission. Windows prompts and the lock screen still cannot be controlled. **What it costs:** that part then runs as administrator at every sign-in without Windows asking, and takes input from any program that runs as you and reads Trace's key, and Trace is installed per user, in a folder your account can write to, so any program running as you could replace Trace's program there and get administrator rights without a prompt; and anyone viewing the screen controls apps running as administrator. Turning it off asks permission again to remove the task. Turning sharing off stops the service and removes the sign-in entry and the Tailscale path (an administrator task left registered starts nothing while sharing is off). The switch is `screen-share.json`.
- **Phones.** A computer passes linked computers' channels on to its phones, never to other computers, so channels cannot loop. Every channel the phone sees names its computer, and the phone can switch between computers. The phone also asks its computer for a phone key to each other linked computer (issued as "<phone> (through <computer>)"; asking again replaces it). When its own computer does not answer, the phone app opens from its saved copy and connects straight to another computer with that key, then switches back when its computer answers. Those computers accept requests from the phone app's origin only when it is one of your computers' tailnet addresses, and still require a key. Phone keys never start or stop channels.

## Workspace

- Open a local project and launch each engine independently. CLIs inherit local authentication, environment, Git context, hooks, and tools. There are no direct model API requests or approval-bypass flags.
- Run **1–8** configured panels (each runs its own CLI, so more panels use more memory); duplicate, close, drag, resize, split into rows/columns, arrange a grid, or isolate a channel. Panels may share the root or use independent repository folders. Launch settings lock while running.
- Click a terminal to type or paste. **Interrupt / Ctrl+C** interrupts an operation; **Stop** ends the process. Xterm supports ANSI output, interactive prompts, resize propagation, and a WebGL renderer with fallback.
- **Show explorer** opens a file tree beside the terminals. **Files** provides the larger source preview; **Changes** provides staged, unstaged, untracked, renamed, binary, and conflict diffs. Choose workspace or channel context to review another repository. Refresh after agent changes. **Changes → Delivery** stages, commits, pushes and opens a pull request, each after a native confirmation; nothing discards changes.
- **Ctrl+Shift+P** (Cmd+Shift+P on macOS) opens the command menu. Switching pages retains the same terminal and scrollback.

**Closing the window** (from 1.34.0) hides Trace to its icon in the tray (the menu bar on a Mac): channels, the phone, linked computers and alerts keep running. The icon's menu says how many channels run and has **Show Trace** and **Quit Trace**; clicking the icon, opening Trace again or an alert shows the window. The first time, a notice says where Trace went. Quit (the icon's menu, or the app menu on a Mac) stops the channels as before, and with **Start channels again when Trace opens** they come back on their conversations. **Settings → Preferences → Keep running when the window is closed** (on by default) turns this off. Quitting, reloading, or closing with that off stops the app's PTYs. The app restores folder bindings, models, raw settings, and layout as **idle** panels. It does not attach to old PIDs. From 1.32.0, the channels running when Trace quits start again when it next opens (**Settings → Preferences → Start channels again when Trace opens**, on by default; per computer): each agent on its saved conversation, each shell afresh, Round Table seats too so the table opens again. An agent channel with no saved conversation stays stopped, since starting it would begin a new one. The list is written as Trace quits (`resume-on-start.json` in Trace's storage folder) and read once by the next start: reloading the window, or a start after a crash, starts nothing. The programs that were running inside the channels do not come back. **Start** and **Restart** start a new CLI process that resumes the channel's conversation, unless **Start a fresh conversation next time** was chosen in its settings. Detached background jobs and remote processes have their own lifetimes.

File previews are bounded to 1 MiB / 4,000 rendered lines; folders list up to 500 entries. UTF-8 and BOM-marked UTF-16 are supported. Links and special files cannot be opened; Git metadata is hidden. Git commands have a ten-second timeout and 2 MiB output limit; lists cap at 1,000 changed paths. Limits and unsupported encodings are reported in the interface.

## Raw engine controls

Blank fields inherit local CLI settings. Suggested model names are editable examples; your CLI and account determine model availability.

**Claude Code:** model maps to `--model`; manual `thinking.budget_tokens` maps to `MAX_THINKING_TOKENS` only for explicit supported manual-thinking models. Adaptive-thinking aliases/default models are rejected when a manual budget is configured. The budget must be at least 1,024 and smaller than an explicit output limit. Maximum output tokens maps to `CLAUDE_CODE_MAX_OUTPUT_TOKENS`. A session token threshold stops the process **after reported new tokens** (input outside the cache, plus output) reach it; a response may exceed it. Enforcement requires structured transcript usage and advertised `--session-id` support. It is not a hard request-level billing cap.

**Codex:** model maps to `--model`; reasoning maps to `--config model_reasoning_effort="<effort>"`. Choices are `none`, `low`, `medium`, `high`, and `xhigh`; supported efforts depend on the selected model. When advertised, `--no-daemon` keeps the session attached to its PTY.

Windows npm launchers resolve to the official package's declared JavaScript entry and run in Electron's Node mode with argument arrays, without shell interpolation.

## MCP, skills, plugins, and hooks

**MCP servers** inspects Claude's global `.claude.json` (including a custom CLAUDE_CONFIG_DIR / legacy `.config.json` when applicable), project-local server entries, project `.mcp.json`, and Codex's user/project `config.toml`. Environment and header names are displayed without their values. The legacy `~/.claude/mcp.json` is identified if present but is not treated as automatically active in current Claude Code.

Add stdio or HTTP servers, toggle enablement, or explicitly remove them. Claude toggles are project scoped; select a project before toggling its user servers. Edits preserve unknown settings, reject stale inspected files and parse errors, create private backups, and replace the target atomically. TOML comments and formatting may normalize. Enabled means configured; server health, authorization, and project trust are verified by the CLI when it starts. Restart channels after edits.

**Skills & plugins** inspects local `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, skill folders, installed plugin metadata/cache manifests, configured plugin activation, and hook event names. Supported Codex skill and configured plugin activation can be toggled. Instruction files and Claude skills are inspected in place; hook commands are never executed by discovery. Inspection is bounded and does not resolve remote marketplaces or install third-party packages.

## Plan limits

The status bar shows how much of each subscription's limits is used, for example **Claude 5h 6% · wk 12%**, **Codex wk 3%** and **Gemini 5h 3% · wk 2%**, each limit with a small meter while the bar has room for them, amber from 75% and red from 90%. The numbers are the default login's; a named Claude account that one of your channels runs on is added by name once one of its limits reaches 75%. If the last check failed, the numbers dim and a warning mark appears: they are from an earlier check, whose time is in the tooltip. Hover for every limit, account and reset time; click for **Usage**, whose **Plan limits** card shows each limit as a bar, the plan, and **Check now**.

- **Claude:** Trace runs Claude Code's own `/usage` (`claude -p /usage --no-session-persistence`) for the default login and each connected account profile. It makes no model request and saves no session.
- **Codex:** Trace asks Codex's app server for `account/rateLimits/read`, also without a model request. Codex names its limits by length (a 5-hour session on plans that have one, and the week).
- **Gemini CLI:** Trace runs agy's own `/usage` (`agy -p /usage --output-format json`, from agy 1.1.11, which answers it without a model request; an older agy is not asked). Gemini's own models are the session and the week; other model groups (for example Gemini 4 Argon, or Claude and GPT models) are named after their group on **Plan limits** and in the hover.
- Limits are read when Trace opens, every five minutes, and when you return to the window (at most once a minute). Accounts billed by API usage have no session or weekly limit to show.
- A reset time shows as a countdown only when the CLI gives a time in the future; other wording is shown as the CLI wrote it, and a reset time that has passed shows nothing until the next reading. Two Codex limits with the same name are labelled by length, for example **Session (5 h)**, and a Codex reply Trace cannot read says "Codex reported its usage limits in a form Trace does not read. Update Trace."
- On **Plan limits**, a check that failed (the CLI did not answer, could not be started, or reported limits in a form Trace does not read) shows as an error, and a fact about the account (billed by API usage, no limits to show) as a note. In the status bar an engine whose reading holds only such a message reads **no data** (hover for why), and an engine with neither limits nor a message has no item.

## Usage and prices

A Claude Code channel's context is what its latest reply carried (its whole prompt plus its output), out of the window Claude Code reports while it runs. When the conversation is compacted (`/compact`, or by Claude Code itself), the context is what the compaction kept, as Claude Code's log records it, from that moment; an older Claude Code that does not record it shows no context until the next reply.

Usage comes from the CLIs' **local structured JSONL session logs**. Claude sessions are correlated by the app's generated UUID; Codex uses a per-run TUI log directory and thread ID to locate its rollout. CODEX_HOME and CLI authentication are inherited unchanged. Same-directory Codex sessions are not assigned usage when their thread association is ambiguous. Unsupported versions, disabled transcript logging, or missing usage events display unknown values.

Agents a Claude Code channel starts count toward its tokens, cost and session token limit, and toward today's total: the Task tool's agents and a workflow's agents alike (their transcripts under `<conversation>/subagents/`, including a workflow's `workflows/<run id>/`, up to three folders deep). A new workflow agent can be counted up to 5 seconds late. Repeated Claude message snapshots are deduplicated; Codex cumulative events replace earlier totals. Claude cache reads/writes are separate from noncached input. Codex cached input is already included in input, and reasoning tokens are already included in output. Missing reasoning or context limits remain unknown. Context percentage is shown only when the CLI supplies a usage/window pair.

Trace prices Claude, GPT and Gemini models itself, from Anthropic's, OpenAI's and Google's published prices (`shared/model-prices.ts`, with the date they were last checked shown in **Settings → Model pricing**; they are checked again with each release). An installed Trace also looks once a day for a newer list on its downloads page (`catalog.json`: prices and Claude Code's model names only, checked before use, never older than what Trace was built with; nothing about you is sent), so a price change or a new model does not wait for a release. Nothing needs to be entered. Claude's cache writes are priced at the one-hour rate, which is what Claude Code writes. Estimates use the standard price for every request: a prompt long enough for a provider's long-context price (Claude Haiku 5.5 over 100,000 tokens, OpenAI's models over 272,000) is not told apart. Gemini CLI on a subscription is not billed by the token: its cost is what the same use would cost through the API, and a price Google has announced to change on a date is used from that date. To use your own rate for a model, add it in **Settings → Model pricing** in **USD per million tokens**; it comes before the published price. An exact ID wins; otherwise a rate also matches the same model written another way: its name as people write it ("Claude Opus 5.5"), other case, spaces or dots for dashes, or a release date (`-YYYYMMDD`). Context-size variants such as `[1m]` are not merged. Unconfigured models show no cost estimate. Rates are user supplied; estimates are not an invoice and exclude discounts and billing adjustments. The Usage dashboard provides per-run counts, estimates, and the latest 14 active days. Daily totals group entire runs by session start date in local time, including sessions crossing midnight. Usage records retain up to one year and the UI loads the latest 2,000 runs.

## Local storage

All runtime data is outside the source folder, normally `C:\Users\<you>\.coding-hub` on Windows:

| Location | Contents |
| --- | --- |
| `storage.db` | Workspace settings and session run metadata |
| `logs/<run-id>.log` | Terminal output, up to 5 MiB per run |
| `telemetry/usage.db` | Deduplicated usage records and run metadata |
| `day-usage.json` | How far Trace has read each CLI log for the status bar's **Today** and the daily totals so far: log paths, engines, read positions, token totals and Claude message ids, no credentials. Delete it while Trace is closed and the next start reads the last 60 days of logs again, in the background |
| `host-health.json` | The last 100 lifecycle events (starts, stops, crashes) and, from this version, the last 200 moments Trace stopped responding (main process or window); see [troubleshooting](troubleshooting.md#trace-stops-responding-for-a-moment) |
| `preferences.json` | Drive folder, terminal font size, price rates, sync switch, your own Round Table presets (kept on this computer, not synced) |
| `machine.json`, `device-sync.json` | This computer's sync identity and name, and what was last synced between computers |
| `worktrees.json`, `worktrees/<uuid>/` | Managed isolated branches and working folders |
| `updates.json` | Automatic update-check preference |
| `shared-rules.json` | Canonical shared rules and registered project folders |
| `memory/<project>/<note-id>.json`, `memory/.drive-compared.json` | Curated handoffs; note pairs already compared with the Drive copy (a cache, safe to delete) |
| `designs/`, `design-annotations.json` | Left by the Design workspace, which was removed. Trace no longer reads or writes them; backups still include them, and nothing deletes them |
| `coaching/`, `experiments.json` | Curated examples, prepared reports, A/B trial evidence (at most 100 experiments; delete one to make room) |
| `crash-dumps/` | Local crash reports, never uploaded; those older than 14 days are deleted at each start |
| `tasks.json`, `verification.json` | Task scopes, command profiles, recorded check results |
| `agents/<id>.json`, `agents-confirmed.json`, `agents-received.json` | Custom agents (1.40.0): one definition per file (written like configuration files, with a private copy of the old one in `config-backups/`), and the hash of each definition confirmed on this computer; a definition whose hash is not there does not start. `agents-received.json` notes which definitions sync brought from another computer, for the Agents page. The confirmations and that note stay on this computer; the definitions sync. Not in backups |
| `scheduled-jobs.json` | Scheduled jobs (1.39.0): each job's request, folder, agent, schedule and last run. Not in backups |
| `backups/`, `restores/` | Verified backups and separate restored data copies. A backup holds at most 64 MiB: the databases may use all of it, other files 16 MiB each, and a backup that is too large names the file. It never holds this computer's own identity, paired phones, linked computers, removed computers or screen-sharing settings, so a restore keeps the current ones; the first sync after a restore takes the shared templates back and asks about rules or settings that differ. Deleting a backup asks first |
| `remote-unlinked.json` | Computers removed under Other computers, by machine id, which may not link themselves again. Not in backups |
| `runner/` | The background runner (1.36.0): `kits/` (its own copy of Electron as Node, its scripts and node-pty), `secret` (what Trace says hello with), `ports.json` (the ports Trace's hook servers had) and `runner.log` |
| `linked-computers.json`, `screen-sharing.json`, `screen-share.json` | Keys to linked computers, screen-sharing sign-ins (passwords encrypted by the system), and whether this Windows screen is shared |

Finished output retains up to **100 runs for 30 days**; active runs are excluded from pruning. The history viewer shows the last 1 MiB of large logs, strips ANSI escapes, and identifies capped/interrupted runs. Normal closing requests a final settings snapshot, stops processes, and flushes logs. Invalid/future saved data is preserved rather than overwritten. Storage failures do not prevent basic interactive CLI execution.

Storage is local and unencrypted. Logs include whatever a CLI prints, including echoed input. Input, environment variables, and authentication files are not collected separately. To change the storage root, set `CODING_HUB_STORAGE_DIR` to an absolute writable path before launch.

```sh
npm run typecheck
npm test
npm run test:pty
npm run test:memory
npm run test:desktop
npm run test:design
npm run test:profiles
npm run test:workbench
npm run test:enterprise
npm run test:productivity
npm run build
```

The desktop smoke test uses test CLIs and isolated real repositories, databases, and a local Drive-folder fixture. It exercises production Electron/preload, actual PTYs, input/resize/retention/cleanup, file and Git review, unchanged index bytes, usage/cost updates, MCP toggles, skill inspection, shared notes/Drive mirror, restoration, unavailable storage, help search/navigation, matching rules in both engines, and launch rejection for unapplied rules. The standalone memory smoke checks an actual stdio MCP process across Claude/Codex fixture sessions.

Cloud Linux validation does not replace authenticated model completion tests or native Windows/macOS testing. Drive folder mirroring is tested locally; actual Drive authentication/upload is managed by your desktop installation and cannot be verified from the cloud machine. The Windows installer and update lifecycle are prepared; live distribution requires a published release. See [Windows releases](windows-releases.md).

Optional Windows installer and portable build:

```powershell
npm.cmd run dist:win
```

Outputs go into `release/`. Publishing is disabled. Builds are unsigned unless a signing certificate is configured. The output includes Setup.exe, Portable.exe, latest.yml, and an installer blockmap. The build checks PE architecture, native terminal helpers, and application assets, but does not prove native Windows behavior. node-pty uses real filesystem paths, so the package disables ASAR and retains required runtime helpers.

## macOS/Linux and cloud setup

Use `npm ci`, then `npm run dev` on a graphical desktop. Linux source builds need Python 3, make, a C/C++ compiler, and Electron's GTK/NSS/X11 libraries. macOS may require Xcode Command Line Tools. Windows uses supplied ConPTY binaries; native source rebuilding requires appropriate Visual Studio C++ tools and Windows SDK. `npm run rebuild:native` repairs the binding if needed.

For a read-only cloud home, use writable caches:

```sh
npm_config_cache=/workspace/.cache/npm npm_package_config_node_gyp_devdir=/workspace/.cache/node-gyp electron_config_cache=/workspace/.cache/electron ELECTRON_GET_USE_PROXY=1 NODE_USE_ENV_PROXY=1 npm ci
```

Keep TLS and package/artifact integrity checks enabled. `CODING_HUB_TEST_NO_SANDBOX=1` is a test-only desktop runner flag for restricted Linux CI; the production launcher does not supply it. `npm run dev:web` renders a browser preview, which cannot access local processes or native integrations.
