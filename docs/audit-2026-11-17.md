# Audit of Trace 1.22.0 (17 November 2026)

A read-only audit of the repository at `6b0e9b9` (the released 1.22.0), run on the Windows computer where the freezes were reported. The audit itself changed no application code; the fixes made afterwards are in [audit-2026-11-17-fixes.md](audit-2026-11-17-fixes.md). Every finding, with the independent check made of it, is in [audit-2026-11-17-findings.md](audit-2026-11-17-findings.md).

## How it was done

- **Twelve auditors** read the code by area: three looked only for the freezes (recurring work, blocking calls, the window and GPU side), nine covered each subsystem.
- **Each finding was checked by a second, independent reader** who opened the cited code and tried to disprove it, measuring on this computer's real data where possible (read-only; databases through copies).
- **Result of the first round:** 148 findings (a second round over the files it missed added 36; see "Second round"). 118 were confirmed and 30 are plausible (the code is as described, but the trigger or impact was not fully established). None was refuted, but the checkers lowered the severity of many and corrected several numbers. After checking: 3 high, 24 medium, 121 low. Many entries describe the same defect from different angles.
- **Baseline checks at `6b0e9b9`:** `typecheck` passes; `npm test` has 769 passed, 3 skipped and 4 failed (the known symbolic-link `EPERM` tests on Windows without Developer Mode); `test:release` passes 8 of 8. Smoke tests were not run: the installed Trace was in use.

## The 1 to 3 second freezes

**No freeze was caught while it happened, so the cause below is the best-supported explanation, not a proven one.**

What was measured on the installed 1.22.0:

- **Main process, 15 minutes, four requests a second:** median answer 1 ms, 99th percentile 6 ms, worst 263 ms. No stall of 300 ms or more. The audit's own agents were running in a Trace channel during the probe; no channel was started and no session ended in that time.
- **Main process, a further 45 minutes:** 10,256 samples, worst 124 ms, no stall of 150 ms or more. Again no channel started or ended in that time, which fits the event-tied cause below but does not prove it. The probe cannot see a stall inside the window itself.
- **Timers:** the 30-second tick blocks about 90 ms, the status bar's usage read 20 to 40 ms every 15 seconds, the usage poll about 1 ms per channel. No timer reaches one second in steady state.
- **GPU process:** the health record has one GPU crash (2026-11-15 16:25 UTC) and none since. The 23 crash dumps in `~/.coding-hub/crash-dumps` are from the GPU smoke test, not from normal use (see "Crash dumps" below). Windows logged no display-driver reset and no application hang for Trace in 14 days.

What does reach 1 to 3 seconds: **memory sync with Google Drive, done synchronously on the main process, tied to events instead of the timer.** While it runs, the window, every terminal and the phone all wait.

| # | What | Where | Measured here | When |
|---|---|---|---|---|
| F1 | The first comparison of a project after each start reads every note on both sides, including notes whose sizes already match | `electron/services/hub/drive.ts:89` | 1.0 to 1.1 s (AI Scribe, 336 notes); 1.9 to 2.2 s (home folder, 785 notes) | Once per affected project per start: at the first channel start there, or on a 30-second tick |
| F2 | Every channel start and every end-of-session summary lists the project's whole Drive folder | `electron/services/hub/service.ts:49` | 0.5 s (home folder), 0.25 s (AI Scribe), 0.08 s (this repository) | Every start. 15 of the last 42 starts came within 5 seconds of the previous one, so they add up. Grows about 0.5 ms per note |
| F3 | Notes are copied to and from Drive one at a time | `electron/services/hub/drive.ts:96` | 16 ms per note: 3.9 s for 250 notes on 2026-11-15; 0.1 to 0.3 s for the usual 5 to 19 | Whenever notes are waiting, for example after agents write several handoffs |

F1 exists because two projects here can never take the fast path: 250 AI Scribe notes and one home-folder note have the same content on both sides in different line endings.

Shorter hitches that add to these:

- **Day usage** (`electron/services/hub/day-usage.ts:34`): after every start, about 90 passes of 20 to 116 ms over the first 50 seconds, because 1.4 GB of CLI logs are read again from the beginning. Afterwards 20 to 40 ms every 15 seconds.
- **Device sync on the 30-second tick** (`electron/services/hub/device-sync.ts:167`): about 80 ms, half of it recomputing all usage; this computer's usage file is rewritten on Drive while any agent runs.
- **`reg.exe` run synchronously** (`electron/services/cli/discovery.ts:53`): 26 to 41 ms whenever its 5-second cache has expired, on every Git call, start and plan-limits check.

On the window side:

- **Chat channels** (`src/state/chat-store.ts:67`, `src/components/chat/ChatView.tsx:136`): every streamed token re-renders the whole thread. Measured in headless Chrome with real histories: 2.5 ms per token at 200 items, 26 ms at 1,555, 38 ms at 3,109. This makes a very long chat or Round Table sluggish while a reply streams. It is not a sudden stop.
- **WebGL terminals** (`src/runtime/terminals.ts:119`; the setting is on here): a lost graphics context stops terminals drawing for up to 3 seconds, then that terminal stays on the slower renderer until restart. Rare here.
- **Round Table steps** (`electron/services/workbench/repository-state.ts:45`): every changed file is hashed on the main process, 0.68 s at 2,000 files. Not triggered here (at most 4 changed files).

**Nothing records a freeze** (`electron/services/storage/host-health.ts:29`): no event-loop lag in the main process, no long task or lost graphics context in the window. This is why every freeze report starts from zero.

Suggested order of work:

1. `drive.ts:89`: skip pairs whose sizes are equal, as the fast path at line 82 already does; keep the compared pairs on disk so a restart does not repeat the work; read the rest with `fs.promises`.
2. `service.ts:49`: make `trackProject` use `syncLater` (asynchronous), and await it in the launch path where the notes are needed.
3. `drive.ts:96`: copy notes asynchronously, a few at a time, and stop listing the Drive folder once per note (`memory.ts:81`).
4. Record stalls: `monitorEventLoopDelay` in the main process, a long-task observer and a heartbeat in the window, in their own capped list in host health, with the name of the job that was running.
5. `day-usage.ts`: save each log's offset and the day totals, and read in a worker.

## Other findings to act on first

### Bugs

- **Workflow agents' tokens are not counted** (found during the audit from the person's report, not by the auditors). Trace reads `<conversation>/subagents/agent-*.jsonl` only; agents started by a workflow are written to `<conversation>/subagents/workflows/<run id>/agent-*.jsonl`. For the audit's own session Trace recorded 195,648 new tokens while the 37 workflow agents used 9,860,001. The same shallow lookup is at `electron/services/hub/telemetry.ts:39`, `:176`, `:252` and `electron/services/hub/day-usage.ts:73`. Usage, today's total, cost, budget warnings and a session token limit all miss them.
- **Ctrl+R reloads the window and Ctrl+W closes it** (`electron/main.ts:417`): Electron's default menu is still active behind the hidden menu bar. With focus outside a terminal, either key stops every running channel without asking.
- **Closing a Round Table's channel with the tile's X discards its review findings** (`src/runtime/use-native-host.ts:193`); only the table's own close saves them to memory.
- **Images attached to plan feedback are dropped** (`electron/services/chat/review-chain.ts:265`) while the thread shows them as sent.
- **A linked computer's chat thread is emptied whenever a local channel changes** (`src/runtime/terminals.ts:261`).
- **Close on a tile stops a running agent at once**, with no question and no undo (`src/components/SessionTile.tsx:150`).
- **Price rates here match no model** (`electron/services/hub/telemetry.ts:49`): the rates are named "Claude Fable 5.2" and "Claude Opus 5.5", the CLIs report `claude-fable-5-2` and `claude-opus-5-5`, so all usage on this computer is unpriced. Renaming the rates to the model IDs fixes it today; the code should match both forms.
- **Backups will fail once `usage.db` passes 16 MiB** (`electron/services/workbench/backups.ts:99`), about late December at this computer's rate. No backup has been made here yet.
- **Restoring a backup drops phone pairings, linked computers and this computer's identity** (`electron/services/workbench/backups.ts:15`); open since the October audit (S01).
- **Phone access off and on loses the `/api/screen` path** (`electron/services/remote/tailscale.ts:101`): the cause of the known open item. `serve --https=443 off` without `--set-path=/` removes every handler on the port, and only `/` is put back.

### Security

- **Auto-link gives a full computer key with no code and no prompt** (`electron/services/remote/remote-server.ts:692`) to any program on a device signed in to the same Tailscale login, or on this computer. A computer key can add and start a shell channel and open the Windows screen. It needs code already running on one of the person's own devices; the feature is on by default and has a switch.
- **A submodule's own Git filter still runs when Trace only reads a repository** (`electron/services/repository/git-safety.ts:14`); reproduced in a scratch repository. Viewing a crafted folder runs its program.
- **The administrator screen service runs code and trusts a list the person's own account can write** (`electron/services/remote/screen-share.ts:43`). The option is off on this computer.
- **Published builds are unsigned** (`electron-builder.cjs:25`): known and documented; updates are trusted on the feed alone.

### Release and tests

- **Release does not check the Windows release candidate** and publishes an installer that was never started (`.github/workflows/release.yml:97`). Known and manual by design; a one-line gate would close it.
- **`scripts/desktop-smoke.cjs` line 277 (open item):** the step picked the first extension row, which on this computer is a skill from `~/.agents/skills`. `6b0e9b9` redirects `USERPROFILE` on Windows, which should fix it here; `HOME` is not redirected, so a Mac or Linux computer with that folder still fails. `test:desktop` was not run in this audit.
- **Never tested before release:** the memory server over stdio, a real PTY and the Windows screen service (`.github/workflows/ci.yml:34`). 57 of 96 test files are not type-checked (`tsconfig.electron.json:14`).

### Shared rules in tracked files

`electron/services/hub/rules.ts:19` writes the shared rules as a block into each project's `CLAUDE.md` and `AGENTS.md`. Every project therefore shows two modified tracked files with mixed line endings, a checkout or fresh clone removes the block and the next start there is refused, and a Claude session in this repository receives the same 1,878 characters four times. Passing the rules at launch, as memory already is, would remove all of this.

## Crash dumps

The 23 dumps in `~/.coding-hub/crash-dumps` are GPU-process dumps from 2026-11-15, written by `scripts/gpu-crash-smoke.cjs` runs. They landed in the real data folder because Trace passes its crash-handler pipe (`CHROME_CRASHPAD_PIPE_NAME`) to every channel (`electron/services/cli/discovery.ts:89`), so an Electron app started from a channel reports its early crashes to the installed Trace. Removing that variable from the environment given to channels fixes it.

## Not covered

- Nothing was run on a Mac, on a real phone, or through the installed app's window.
- Smoke tests (`test:desktop`, `test:remote`, `test:pty`, `test:memory`) were not run.
- Whether the release candidate passed on `6b0e9b9` was not looked up.
- Of 222 source files in `electron/`, `src/`, `shared/` and `phone/`, the first round's auditors listed 191 as read (some only in part). The 31 not read were the stylesheets, `shared/help-content.ts`, `src/components/ExperimentsPanel.tsx` and about twenty `shared/*.ts` contract and pure-logic files. The second round below covered them.

## Second round

Three more auditors read the 31 files the first round missed, with the same independent check: 36 findings, 28 confirmed and 8 plausible, none refuted; 5 medium and 31 low after checking. None concerns the freezes: the stylesheets hold no rule that is costly to draw with eight live terminals.

The five medium findings:

- **Hierarchy table: the builder is never told why a finding was reopened** (`shared/findings.ts:86`). Its next fix prompt lists the finding with the original text only.
- **Pasting more than 4,096 characters into a linked computer's terminal sends nothing**, with no message (`src/runtime/linked-terminals.ts:49`; the host's limit is at `electron/main.ts:252`).
- **Applying a template that holds a Round Table always fails**, after shared rules and checks were already written (`electron/services/workbench/workflows.ts:75`).
- **A channel's hover controls have had no row of their own since 1.16.1**: they are drawn over the header and the terminal (`src/tile.css:71`).
- **Help says Trace adds no permission-bypass flags** (`shared/help-content.ts:101`); by default it starts agents with edits allowed, and Full access bypasses prompts.

The rest are in the findings document under "Second round".
