# Codex models and stability — v1.7.2

## Choosing a Codex model

Open the settings button on a Codex tile. The Model input queries the installed official `codex app-server` through its stdio protocol: initialize, initialized, then model/list. Every pagination cursor is followed, including hidden models. Suggestions use the returned `model` value, never an internal picker ID. Type to filter the suggestions or enter an exact custom ID. Refresh Codex models reloads the catalog after login, account/configuration changes or a CLI update. Discovery is bounded by a timeout and size/page limits; failures are shown instead of inventing a fallback list.

This replaces the fixed two-model suggestion list. No coding thread or prompt is created by catalog discovery, and the application makes no direct provider API request. The CLI inherits your environment, authentication and working directory; it may contact its provider to refresh its catalog. The list describes what that CLI exposes, not a guarantee of entitlement, billing or a successful paid completion. A catalog default may differ from the model in your own CLI configuration.

The selected model's reported reasoning levels populate the effort control, including levels outside the previous fixed list. Changing to a catalog-listed model clears an incompatible previous reasoning override to CLI default and displays a notice. Explicitly selected raw values are passed unchanged to the CLI. Custom models and older CLIs can still use editable model IDs and CLI defaults when catalog discovery is unavailable.

Blank model and effort fields add no override. Existing saved overrides are preserved until you edit them. For recovery, **Use Codex CLI defaults** clears the model, effort and next-launch resume ID. The next launch starts a new conversation; the previous native conversation remains on disk and can still be found through history. While a session runs, the tile shows the model associated with its usage record when available, with the requested override in its tooltip. Usage can inherit the requested model until the CLI writes model metadata. Idle tiles show the next launch's requested model or CLI defaults.

## Application stability

Software terminal rendering is the default. **Settings → Enable terminal WebGL acceleration** retains optional accelerated rendering; restart the app after changing it. Context-loss cleanup also tolerates disposal errors. This is a conservative rendering choice, not a diagnosis of the user's reported Windows crash.

Session and login managers protect event delivery so a disappeared renderer does not turn a notification error into an uncaught host exception or prevent process exit cleanup. Storage/usage/update notifications use the same guarded native delivery. Final telemetry errors do not block the CLI exit notification. Renderer terminal-display errors surface in the tile rather than escaping the IPC listener.

If the renderer process crashes, the native host records the reason, stops its coding/login terminals, and offers reload of the last saved workspace as idle tiles. If process cleanup fails, recovery is blocked and reports the owned coding PIDs instead of claiming they stopped. In-page navigation such as the home link keeps sessions alive; an actual document reload still cleans up owned terminals. This cannot recover unsaved React drafts or an interrupted CLI operation. If the native host itself crashes, this release records what it can and enables local native crash dumps; it does not claim to recover a terminated native host.

## Local diagnostics

Expand **Settings → Running application → Application stability & crash diagnostics**. The lifecycle report indicates whether the prior run finished a clean shutdown and includes at most 100 lifecycle entries. An unclean marker can also mean force quit or power loss. Recording starts with this release, so older crashes have no report from this mechanism.

`host-health.json` contains lifecycle metadata only: timestamps, event types, engine start markers, fixed native delivery channels, Electron exit reasons/codes and uncaught-exception origin. Prompt text, terminal output, raw exception messages/stacks, account details and environment values are excluded. Failure to write this diagnostic store does not block live sessions.

Native dumps live in `crash-dumps` under the active data directory, normally `~/.coding-hub`. Uploading is disabled. Dumps may contain process memory; they are not included in curated Drive memory, ordinary backups or diagnostic support exports. Do not publish dumps or credentials in the repository. The source archive contains application code only.

## Validation and remaining limits

The implementation was verified against the protocol generated by the installed official Codex CLI 0.159.2 and successfully queried its actual model catalog in this Linux cloud environment without sending a task. This was not a query of the user's Windows account.

Unit checks cover all-page/hidden model discovery, exact CLI model values, future/raw reasoning levels, coalesced requests, malformed/error/timeout/cursor-loop handling, shutdown rejection, fresh-default recovery, event-delivery exceptions, bounded health records and clean/unclean restart markers. The native models/stability smoke uses real Electron IPC and fixture CLI processes to verify catalog population, incompatible reasoning reset, exact model delivery, settings persistence, software rendering, and deliberate renderer-crash recovery with a running Claude process. Both Windows CI workflows include this new suite.

Validation passed: 151 unit tests, six release checks, the production build/type checks, seven Electron desktop suites (including models/stability), and standalone MCP/native PTY checks. The coaching smoke now verifies the actual received readiness event and latest visible terminal size line separately, because the readiness banner can be in scrollback in a short software-rendered tile; request delivery and visible error assertions remain intact.

The user's reported full Windows app close while using Claude has not been reproduced. There is no crash log from that installation, and this environment cannot execute or inspect that Windows desktop. These defenses and diagnostics do not establish its root cause or prove the crash is fixed. If it happens after this update, restart the app and inspect its lifecycle report; a main-process/native fault may require the local dump or Windows crash-event details in a private diagnostic workflow. Real Windows official-CLI/account execution and native signing/installation remain separate validation requirements.

The dependency findings documented in the v1.7.1 audit still apply: the reviewed production dependency audit was clear, while development styling/build-tool chains retain advisories. This release does not silently migrate those tools.
